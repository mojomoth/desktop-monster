# v0.8 수집 정책 측정 결과

등록한 점검 80개와 검증 400개가 모두 12시간을 완료했고 원시 기록 검증을 통과했다. v0.7의 성장 수치와 콘텐츠 조건은 유지했다. 아래 결과는 **코어 시뮬레이션의 정책 비교**이며 사람의 재미, 선호, 리텐션 또는 Steam 출시 품질을 판정하지 않는다.

## 조건과 완료 근거

[등록 프로토콜](EVALUATION_PROTOCOL.json)의 동일한 새 게임 상태에서 정책마다 같은 seed를 짝지었다. 점검은 20001–20020 × 4정책, 검증은 30001–30100 × 4정책이다. 점검 20개와 검증 100개는 분리된 집합이며 아래 수치 표는 모두 **정책별 검증 100개**만 사용한다. 점검 결과를 본 뒤 수치, 정책, seed 또는 평가기를 조정하지 않았다.

| 정책 | 영웅 선택 | 동료 관리 |
|---|---|---|
| A | 표시된 첫 카드 | 없음 |
| B | 영구 수집 이력에서 미보유 희귀 → 미보유 일반 → 첫 카드 | 없음 |
| C | 표시된 첫 카드 | 기존 consume-weakest |
| D | B와 같음 | 기존 consume-weakest |

4정책 공통으로 720분, 100ms tick, 1초 관찰, 600초마다 메뉴 방문, 구매·다시 뽑기 없음이다. 입력은 보존한 v7 시뮬레이터의 `engine.attack('keyboard')`를 500ms마다 한 번 실행하는 초당 2회 균등 입력이다. Electron 성능 관측의 keyboard/mouse 교대 합성 IPC와 별개이며 실제 OS 입력이나 사람의 작업 습관을 재현한 결과는 아니다.

B/D의 동순위는 원래 카드 표시 순서를 유지한다. C/D는 각 방문에서 영웅 선택 후 최대 한 번, 생산 코드의 `companionPower` 오름차순과 `id.localeCompare('en')` 순으로 첫 개체를 마지막 개체에 소모한다. 2개체 미만이면 실행하지 않으며 종 또는 파티를 보호하지 않는다. 이 봇 정책을 제품 자동 관리 기능이나 사람에게 가장 좋은 선택으로 추가하지 않았다.

[측정기](../../.harness/v8/measure.mjs)는 원본 v7 시뮬레이터와 기존 소모 함수를 재사용한다. 한 생산 코어 엔진과 주입 RNG를 유지하며 복사된 상태의 카드 보기 순서만 조정한다. 원래 후보 순서·선택 ID·실제 성공한 획득·명단 편입/방출·소모 전후 상태를 보존했다. 검증기는 capture → 같은 시각 consume 순서로 명단을 재구성하여 현재 종/개체 수와 30명 점유 시간을 원장에 대조했다.

점검은 workers2로 05:47:38–06:02:59 UTC에 완료했다. 별도 verify와 evaluator freeze 후, 승인된 병렬 수 변경을 위해 첫 validation child PID65296만 SIGTERM으로 중단했다. 원래 [FAIL/종료 기록](../../.agentdoc/v08-20260914T050544Z/collection/attempt01/completion.json)은 그대로 보존했다. 중단 시 완료된 validation 원시는 0개였다. 동일 output/freeze/binding으로 PID65301이 workers4에서 재개했고 400개 전부 완료했다. 제품·평가기·seed 변경은 없었다.

검증 시뮬레이션은 2026-09-14T06:03:04.247Z–2026-09-14T06:42:57.236Z, 39분 53초였다. 전체 원시 검증까지 마친 최종 상태는 [resume-workers4/completion.json](../../.agentdoc/v08-20260914T050544Z/collection/attempt01/resume-workers4/completion.json)의 **2026-09-14T06:43:10.986727Z PASS**다. 이는 완전한 행렬과 원시 무결성의 통과이며 새 성장 속도 합격선을 뜻하지 않는다.

## 수집 결과

표는 중앙값 [p10, p90]이다. 동결 평가기의 정렬 후 `floor((n-1)×q)` 분위수를 사용하고 표시만 소수 둘째 자리로 반올림했다.

| 지표 | A | B | C | D |
|---|---:|---:|---:|---:|
| 처음 획득한 영웅 종류 | 50 [50, 50] | 67 [65, 68] | 50 [50, 50] | 68 [66, 68] |
| 실제 명단 편입 개체 수 | 30 [30, 30] | 30 [30, 30] | 100 [97, 101] | 100 [97, 101] |
| 한 번 이상 포획한 고유종 | 27 [25, 29] | 27 [24, 29] | 69 [66, 72] | 70 [65, 74] |
| 종료 시 명단 고유종 | 27 [25, 29] | 27 [24, 29] | 26 [24, 28] | 26 [24, 28] |
| 명단 포화로 방출된 사건 | 2444 [1188, 4031] | 2790 [1346, 4022] | 4145 [2851, 5336] | 3911 [2816, 5422] |
| 이전 미포획 종의 방출 사건 | 1947 [944, 3211] | 2222 [1058, 3165] | 2466 [1693, 3145] | 2294 [1577, 3309] |

영웅 종류는 최초로 선택하여 영구 수집에 편입한 종류 수다. 포획은 코어의 실제 명단 편입만 포함한다. `novelReleases`는 **그 시점까지 포획한 적 없는 종의 방출 사건**이며 같은 종의 반복 방출을 포함한다. 방출을 신규 획득이나 서로 다른 종 수로 계산하지 않았다.

수집 공백은 2–12시간 양 끝 경계를 포함하여 첫 영웅 획득/첫 종 포획 사이에서 가장 긴 간격이다. B/D의 중앙값 600초는 **600초 메뉴 방문 정책의 영향을 받는 관측**이다. 실제 이용자가 10분마다 보상을 받는다는 보장이 아니다. 처치 고유종까지 포함한 공백의 중앙값은 A/B/C/D에서 각각 170/10/49.97/10분이었다. 8–12시간 첫 처치 고유종은 모두 중앙값 0이며, 0보다 큰 seed는 A 5/100, B 3/100, C 0/100, D 0/100이었다.

## 관리 비용

아래의 서로 다른 소모 종, 마지막 개체를 소모한 서로 다른 종, 종료 명단에서 사라진 종은 같은 검증 원장의 종 ID를 중복 제거해 추가 집계했다. 평가 목표나 성공선을 추가하지 않았다.

| 지표 | A | B | C | D |
|---|---:|---:|---:|---:|
| 소모 실행 횟수 | 0 [0, 0] | 0 [0, 0] | 71 [68, 72] | 71 [68, 72] |
| 소모 재료에 포함된 서로 다른 종 | 0 [0, 0] | 0 [0, 0] | 54 [50, 57] | 55 [51, 59] |
| 마지막 개체 소모 사건 | 0 [0, 0] | 0 [0, 0] | 57 [52, 61] | 57 [53, 62] |
| 마지막 개체를 소모한 서로 다른 종 | 0 [0, 0] | 0 [0, 0] | 44 [40, 49] | 45 [41, 49] |
| 과거 포획했으나 종료 명단에 없는 종 | 0 [0, 0] | 0 [0, 0] | 43 [39, 47] | 44 [40, 48] |
| 당시 활성 파티 개체 소모 사건 | 0 [0, 0] | 0 [0, 0] | 3 [2, 5] | 3 [2, 5] |
| 종료 시 명단 개체 수 | 30 [30, 30] | 30 [30, 30] | 29 [29, 29] | 29 [29, 29] |

`lastSpeciesLosses`는 **그 종의 마지막 개체를 소모한 사건 수**다. 같은 종을 다시 잡았다가 또 소모할 수 있으므로 서로 다른 종 수와 다르다. 누적 포획 고유종 증가와 현재 보유 고유종 증가도 구분해야 한다. C/D는 중앙값 71회 관리로 실제 편입을 30개체에서 100개체로 늘렸지만, 종료 명단의 고유종 중앙값은 26종이고 마지막 개체 소모는 57회였다. 한 자리씩 비우는 이 정책에서도 30명 포화 시간은 중앙값 약 10.8시간이었다.

## 자격·노출·획득의 차이

각 셀은 **자격 충족/한 번 이상 노출/실제 획득한 seed 수(각 분모 100) · 획득자 중 획득 시간 중앙값**이다. 미획득자는 시간 중앙값에서 제외되며 분모와 미획득 수를 숨기지 않는다. 원본 JSON에는 전체 집단 분위수와 미도달 수가 별도로 남아 있다.

| 영웅 | A | B | C | D |
|---|---:|---:|---:|---:|
| h58 심해 기사 | 100/100/0 · — | 100/100/100 · 130분 | 100/100/0 · — | 100/100/100 · 120분 |
| h62 천공 수호자 | 100/100/0 · — | 100/100/100 · 160분 | 100/100/0 · — | 100/100/100 · 140분 |
| h70 별밤 계승자 | 88/87/0 · — | 94/94/94 · 380분 | 100/100/0 · — | 100/100/100 · 290분 |

A/C의 희귀 3종 선택 0회는 첫 카드 선택 정책에서 발생했다. 이를 사람이 희귀 영웅을 거절한 것으로 해석할 수 없다. 동시에 h70은 A에서 12/100, B에서 6/100이 12시간 내 자격에 도달하지 못했으므로 후기 제한을 전부 카드 선택 탓으로 돌릴 수도 없다.

## 동일 seed의 정책 차이

각 셀은 100개 대응 seed에서 먼저 차이를 계산한 뒤 구한 중앙값 [p10, p90]이다. 정책별 중앙값끼리 뺀 값이 아니다. 음의 공백 차이는 해당 모델에서 간격이 짧아졌다는 뜻이다.

| 대응 차이 | 첫 영웅 획득 종류 | 누적 포획 고유종 | 종료 명단 고유종 | 최장 수집 공백(분) |
|---|---:|---:|---:|---:|
| B-A | 17 [15, 18] | 0 [-3, 2] | 0 [-3, 2] | -160 [-180, -140] |
| C-A | 0 [0, 0] | 42 [39, 46] | -1 [-4, 2] | -120.02 [-149.98, -99.92] |
| D-B | 0 [0, 2] | 43 [38, 47] | -1 [-3, 2] | 0 [0, 0.06] |
| D-C | 18 [16, 18] | 0 [-4, 7] | 0 [-2, 2] | -39.96 [-59.98, -20] |

B−A와 D−C는 신규 영웅 선택 정책의 영향을, C−A와 D−B는 기존 동료 관리 정책을 추가한 영향을 보여 준다. 선택한 영웅의 버프·속성과 소모한 동료의 성장도 이후 전투에 반영되므로 카드 표시만의 효과나 사람의 최적 전략으로 해석하지 않는다.

기존 첫 카드/무관리 봇의 후기 공백에는 정책과 30명 명단 제한이 섞여 있었다. 영웅 수집은 신규 선택으로 늘었고, 동료는 자리를 비우면 새로운 종이 실제로 편입되었다. 그러나 관리 비용이 컸고 후기 첫 처치의 새로움도 드물었다. 따라서 수치 조정 없이 수집·명단·손실 정보를 명확히 하는 v0.8 방향은 이 결과와 맞지만, UI 개선만으로 후기 재미 문제가 해결되었다고 결론내리지 않는다. 사람의 실제 업무 중 경험과 다음날 재방문 관측은 별도로 필요하다.
