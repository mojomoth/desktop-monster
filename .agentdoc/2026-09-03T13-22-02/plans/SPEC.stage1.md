## Summary

DesMon is a BongoCat-style macOS desktop companion: a small transparent,
frameless, always-on-top pixel-art overlay in which every keystroke or mouse
click makes a sword-wielding pixel knight attack a monster. Monsters have HP
bars; killed monsters scatter into pixels, drop items that are auto-collected,
grant XP, and are replaced by a stronger monster, while the hero levels up.
v2 (0.2.0) adds: every 8th monster is a boss that can be captured into a
30-companion roster that attacks alongside the hero; fever mode; a companion
lifecycle (consume / fuse / reincarnate / sacrifice / rebirth); unbounded
A–Z-suffixed damage numbers on native `bigint`; a Collection & Battle window;
and a leaderboard + asynchronous PvP with companion stealing against a small
Node server (`src/server`, Render free tier) — offline-first, the game never
waits on the network. Built with Electron + TypeScript, all art and sound
generated from code committed in-repo, verified end-to-end by the frozen
AGENTS.md command contract (`npm test && npm run lint && npm run typecheck`,
`npm run smoke`, `npm run package`, `npm run start:server`).
v3 (0.3.0) adds: elemental types with a fixed 5-cycle chart (fire → wind →
earth → water → dark), hidden per-species sizes, a 5-member overlapping party
auto-picked by effective power against the field monster, PvP with an
opponent preview + a manual PvP-only party + a deterministic battle replay in
the overlay, a low-chance (15 %) attacker-only steal with a native
notification and a 24 h reclaim window, and a bigger 480×300 overlay with 1×
units — served by a second Render service `desmon-server-v3` built from
branch `v3`.

## Assumptions

1. Hero stands on the LEFT facing right; monster on the RIGHT facing left — the requirement allows either side; fixing one makes rendering and tests deterministic.
2. Attack triggers are every `keydown` (OS auto-repeat included) and every `mousedown`, each counting as exactly one attack; key-up, mouse-up, scroll and mouse-move do not — matches the BongoCat per-event feel and is the simplest countable rule.
3. Progression formulas are frozen to GAME_ARCHITECTURE §2 as amended by GAME_DESIGN_V2 §1: `damageForLevel(l)=l`; crit chance 10% × multiplier 2; `monsterMaxHp(i)=⌊10·115^i/100^i⌋` computed as an exact `bigint` (`(10n*115n**i)/100n**i`, equal to the v1 double `⌊10·1.15^i⌋` for every i < 199); `xpReward(i)=5+3i`; `xpToNext(l)=⌊20·1.4^(l−1)⌋`; coins per kill `1+⌊i/3⌋`; trinket chance 25%; hero damage = `level × (crit ? 2 : 1) × (fever ? 3 : 1) × (1 + souls)` — exact formulas make every AC numerically decidable.
4. Exactly 5 monster species (slime, bat, ghost, golem, dragon) cycle forever, with a palette tint per `tier = ⌊index/5⌋`; every 8th monster (`index % 8 === 7`: 7, 15, 23 …) is a boss with 5× HP, 5× XP, 5× coins, a ` BOSS` name suffix and `MonsterDef.boss = true`, drawn at 3× with a crown — 8 is not a multiple of 5 so bosses cycle all species; bounds art effort while making endless scaling visible.
5. Progression is endless: no win state, no final boss. Rebirth at `monsterIndex ≥ 40` is a soft prestige: `souls += ⌊index/8⌋`, `rebirths + 1`, run resets to level 1 / monster 0 while companions, items, coins, kills, bestIndex and nextCompanionId are kept — DesMon stays a companion toy; souls multiply damage by `(1 + souls)`.
6. Trinket items are collection-only counters (5 kinds, weighted) with zero gameplay effect — keeps the engine minimal; coins and trinkets are just HUD/save counters.
7. The save file is `app.getPath('userData')/save.json` (`app.setName('DesMon')` so dev and packaged share it), schema `SaveFileV2` (bigint fields as decimal strings); `parseSave` migrates v1 saves and junk per field (independent fallbacks to `DEFAULT_SAVE`) and never throws — the app must never fail to boot because of a bad save; `serializeSave`/`createEngine` accept `SaveFileV1 | SaveFileV2`.
8. Damage is applied at input time; animations are presentation-only and never gate game logic — keeps the engine deterministic and key-mash-safe.
9. Animation timing state machines (hero IDLE/ATTACK; monster SPAWNING/IDLE/HIT/DYING) are pure functions in `src/core/fsm.ts`, advanced by injected `dt`, consumed by the renderer — the only way animation timing is unit-testable without a DOM.
10. The window is fixed at 320×220 CSS px (internal canvas 160×110, `image-rendering: pixelated`), not resizable, and draggable by mouse-dragging ANYWHERE on the overlay via a custom threshold drag (cursor deltas streamed to main over `desmon:move-window`; a press only becomes a drag after ~4px of cursor travel, so clicks remain attacks and the fallback path keeps receiving `mousedown`) — a full-window `-webkit-app-region: drag` would swallow the fallback clicks, so the CSS drag region stays limited to the legacy 24-px top strip. The default window position is the bottom-right corner of the primary display's work area (which already excludes the macOS Dock / Windows taskbar) inset by a 16px margin.
11. In SMOKE mode the app never touches uiohook, drives a `SimulatedInputDriver` to fire ≥3 synthetic attacks, and prints `SMOKE_OK` only after the renderer reports its first painted frame over IPC — smoke then proves boot + render + input path with zero permissions and zero interaction; under `SMOKE=1` the client is offline by code, `userData` is a fresh temp dir (Assumption 40) and the menu window is never created.
12. All UI text is English only — localization is a Non-Goal.
13. Sound is exactly 4 synthesized WebAudio blips (attack tick, kill arpeggio, level-up fanfare, fever start — an ascending 4-note square sweep), created lazily on first input, with no mute/volume UI — included only because it is trivially achievable without assets.
14. Dependency versions are pinned EXACTLY per GAME_ARCHITECTURE §0.2 (electron 39.8.10, eslint 9.39.4, typescript 5.9.3, typescript-eslint 8.63.0, vitest 3.2.7, vite 6.4.3, electron-builder 26.15.3, @types/node 22.20.0, uiohook-napi 1.5.5, no `^` ranges) plus v2's single pre-approved addition `pg` 8.23.0 in devDependencies only (ponytail rung 5: no stdlib Postgres client) — host Node 20.12.2 is the binding constraint; newer majors break install.
15. Statistical ACs use a fixed seed and tolerance bands (crit 8–12%, trinket 23–27%, PvP 1:3 power → 22–28% win rate, over 10,000 trials) — deterministic because the RNG is injected mulberry32.
16. The tray menu is the settings surface: title row, input-mode status / "Grant Accessibility…" item, separator, `Collection & Battle…` (opens the 420×640 framed DOM window `static/menu.html` with Roster / Ranking / Battle tabs; the tray item is its ONLY opener; never opened under `SMOKE=1`), `Reset Progress`, `Quit` — no other settings UI exists.
17. The overlay is 480×300 CSS px (internal canvas 240×150 at CSS 2×, `image-rendering: pixelated`); hero and monster art render at `SPRITE_SCALE = 1` (each art pixel is one canvas px = 2 screen px; was 2× on a 160×110 canvas in v2), the `LV n` + XP gauge still floats centered above the hero's head, items, damage-number glyphs and HUD counters stay 1×. Normal monsters draw at scale `sizeOf(species)` (1–3), bosses at `sizeOf + 1` (crown centred above, HP bar raised to `BOSS_HP_BAR_Y = 78`); the party draws as an overlapping size-sorted group left of the hero (`partySlots`, `PARTY_X = 8`, step 14/3, largest at the back) — v3 requirement 8 (bigger field, smaller units) with the layout table of GAME_DESIGN_V3 §6; every pinned coordinate changes value in the owning task, no `it(` is deleted.
18. Numbers: monster HP, damage and companion power are native `bigint` (unbounded); coins/xp/level/kills/souls/rebirths/indices stay JS numbers because their curves are linear/logarithmic and cannot approach 2^53 in practice; JSON (save, IPC, wire) never carries a raw bigint — bigint fields travel as decimal strings.
19. `monsterMaxHp` is the exact rational floor `10·115^i/100^i`; it equals the v1 double formula for every index < 199, so v1 exact-value tests keep their values (type edits only, no test deleted; index 5000 has 305 digits).
20. Damage/power text uses truncating A–Z notation (`src/core/bignum.ts`): < 1000 verbatim; else 3 significant digits truncated (never rounded) + bijective-base-26 suffix by thousands-group (A = 10^3 … Z = 10^78, AA = 10^81, ZZ = 10^2106, AAA = 10^2109): 1000 → `1.00A`, 12345 → `12.3A`, 123456 → `123A`, 999999 → `999A`, 1e6 → `1.00B`, 1e9 → `1.00C`; `.` and every letter exist in the 3×5 font; coin/kill counters stay plain `String(number)`.
21. Save schema v2 stores bigint fields as decimal strings (`monsterHp ≥ '1'`); v1 saves migrate field by field (`bestIndex = monsterIndex`, `companions = []`, `nextCompanionId = 1`); junk never prevents boot; `createEngine` and `serializeSave` accept v1 or v2; `nextCompanionId` is raised above every existing `cN` id so re-minting never collides.
22. Every 8th monster (`index % 8 === 7`) is a boss: 5× HP, 5× XP, 5× coins, ` BOSS` name, drawn 3× with a crown; bosses cycle all five species; `loot.ts` is untouched (the engine multiplies the coin amount).
23. Boss kills capture the boss as a companion with probability 0.35 via ONE extra rng draw taken AFTER the loot roll and always consumed (so non-boss seeded event logs stay byte-identical to v1); companions are `{ id 'cN', speciesId, bossIndex, level 1..10, stars ≥ 0 }` with ids minted from `nextCompanionId` (never uuid); the roster holds at most `ROSTER_CAP = 30` — captures and PvP steals into a full roster are void (the draw is still spent).
24. Companion power = `max(1, ⌊monsterMaxHp(bossIndex)/20⌋) · level · 2^stars` (bigint); the field party is the `PARTY_SIZE = 5` companions with the highest **effective** power against the current monster's type (`effectivePower(companionPower(c), typeOf(c.speciesId), monster.type)`; ties → higher raw power → lower numeric id), recomputed every volley; each hits once per 1000 ms of engine time (`COMPANION_ATTACK_MS`) for its type-adjusted power, never crits, ×3 during fever; `companionAttack` carries `effectiveness`; their kills chain into the next monster inside the same volley, drop loot and can capture; no companions → no events and no rng draws.
25. Fever starts when 20 inputs land within 3000 ms of ENGINE time (advanced only by `engine.tick(dt)`; the renderer feeds rAF dt clamped to 100 ms), lasts 5000 ms, triples all damage, then a 10000 ms cooldown blocks re-trigger; never persisted (`toSave()` has no fever field); `feverStart` may precede the `attack` event of the triggering input; a throttled window can over-trigger — deterministic and accepted.
26. Lifecycle ops are pure and total (`applyCollection(state, action) → { state, events } | { error }`, never mutating input): consume (target.level += 1 + food.stars, cap 10, food removed, target ≠ food), fuse (same species + same stars → stars + 1, level 1, bossIndex = max, second removed), reincarnate (level 10 → level 1, stars + 1), sacrifice (removed, souls += 1 + stars), rebirth (Assumption 5), addCompanion (full → error), removeCompanions (unknown ids ignored), pvpResult (lost removed, stolen re-minted via addCompanion, dropped silently when full); only `rebirth` and `pvpResult` emit events; there is no `rosterChanged` action or event — the renderer flushes the save after every `apply`.
27. Hero damage = `level × (crit 2) × (fever 3) × (1 + souls)`; hero level is a minor stat — growth comes from companions and souls; balance beyond these formulas is a Non-Goal.
28. Effects are data presets over the existing 200-slot particle pool, deterministic (index-derived angles and colours, no rng); each species, the hero (cyan; gold `heroSlashSouls` with souls > 0), companions (projectile), bosses (shockwave), captures (sparkle) and fever (aura) have distinct presets per GAME_DESIGN_V2 §8; floats spawn at `barY − 6` of the ACTIVE HP bar so they never overlap the raised boss bar.
29. Collection/Ranking/Battle UI is a second 420×640 framed DOM window (`static/menu.html`, `src/menu/**`, same preload and webPreferences as the overlay) opened only from the tray; the Battle tab is (top to bottom) the name row + `Find opponent`, the `#opponent` panel (name, rank, its PvP party as mini cards in `partyOrder`), the `#party` editor (5 slots, roster picks, `Auto`, `Save party`, live Σ preview), `Battle!`, `#result`, and the `#thefts` inbox with `Reclaim` buttons; the game window owns the engine; main is stateless and relays validated actions (`desmon:menu-action` → `desmon:action`) and the last written save (`desmon:state-changed`) to every window except the sender; main originates exactly ONE action type (`addCompanion` after a successful reclaim, Assumption 49); no hotkey; never opened under SMOKE.
30. Sound is four synthesized blips (v1 three + fever start); `GameAudio.feverStart()`.
31. Identity is `userData/identity.json` `{ name, playerId, token }` held by main only (electron-free module, dir injected); credentials are server-issued on first sync (`POST /v1/players`); default name `Knight-xxxx` (4 uuid chars); display name matches `NICK_RE = /^[A-Za-z0-9_-]{1,16}$/`; a 401 clears credentials (keeps the name), re-registers and retries ONCE per session; the token never enters `save.json` or any IPC payload (renderers only see `{ name, playerId, online }`).
32. All networking lives in main (`src/main/net.ts`: Node `fetch` injected as `fetchFn`, `AbortSignal.timeout(5000)`, JSON only, never throws, every failure is a `NetResult { ok: false, error: 'offline' | 'unauthorized' | 'network' | 'server' | 'cooldown' }`); renderers never touch the network; `baseUrl = process.env.SMOKE ? '' : (process.env.DESMON_SERVER_URL ?? SERVER_URL)` and `SERVER_URL = ''` until the deploy task fills it, so the client is offline by default and `SMOKE=1` forces offline by code (zero fetch calls); sync is inline at three moments (after a save whose roster key `[name, rebirths, companions]` changed, before leaderboard when dirty, ALWAYS before PvP) plus a background re-upload on menu open — no scheduler module; the game never waits on the network.
33. Leaderboard score = deepest monster index reached (`bestIndex`) desc, ties by `rebirths` desc, ties share a rank; stats are self-reported (accept-and-rank): the server validates shape/caps only and is authoritative for the PvP verdict and roster moves alone — no anti-cheat, stated openly in README and handoff.
34. PvP is asynchronous and two-step: `POST /v1/pvp/match` returns the server-picked opponent (rank neighbour above/below by `seed & 1`, else bot `Training Dummy` with the caller's own score and an empty party — never steals, never stolen from) with its stored PvP party and a `matchId` valid for `MATCH_TTL_MS = 120_000`; `POST /v1/pvp { matchId, party }` resolves with the deterministic core battle simulation (`simulateBattle`: alternating front-member blows, hp = power × `BATTLE_HP_MULT = 5n`, cap `BATTLE_MAX_BLOWS = 200`, no rng) via core `resolvePvp(attackerParty, defenderParty, mulberry32(seed), winnerRosterSize)` (exactly 2 rng draws — steal roll `< STEAL_CHANCE = 0.15`, then victim index — ALWAYS drawn); only the attacker can steal (on a win, one uniformly random member of the defender's PvP party, re-id'd `'s' + seed`, unless the winner's roster is full); the loser gets a theft record and can reclaim within `RECLAIM_WINDOW_MS = 86_400_000`; the response carries the blow list (`WireBlow.damage` decimal string) which the game window replays (≤ 12 s) without re-computing; 60 s per-caller cooldown → 429 `cooldown` + `retryAfterSec`; the defender learns of a theft as `removed` on its next upload and via `thefts`; the menu forwards outcomes to the game as `removeCompanions` then `pvpResult { won, stolen, lostId: null, replay }` actions; unknown/expired/foreign match → 410 `match_expired`.
35. Server is a Node 20.12.2 `node:http` + `pg` service in `src/server` (no framework, no `@types/pg` — a 3-member ambient `pg.d.ts`), compiled by `tsconfig.main.json` into `dist/electron/server/**` (excluded from the .app by `!dist/electron/server/**`), `Store` interface with `MemoryStore` (tests, DB-less local runs) and `PgStore` (`DATABASE_URL`, idempotent DDL on every boot, one `players` table, `last_pvp_at double precision`, `count(*)::int`), deployed to Render free tier (oregon) via `.harness/<HV>/loop/render-bootstrap.sh` (v2 service `desmon-server` from `main`; v3 service `desmon-server-v3` from branch `v3`, Assumption 50); free Postgres expires 30 days after creation (documented, recreatable); `/healthz` never touches the DB; rate limit 60/min per key (bearer hash else `ip:<first x-forwarded-for>`), body cap 65 536 bytes → 413.
36. The bigint cutover is one atomic 7-file task; `it(` counts per test file never decrease; pinned lists (`tests/ipc.test.ts` IPC table + preload/handle lists, `tests/tray.test.ts` menu order, `tests/renderer.test.ts` preload regex vs `global.d.ts`, `tests/sprites.test.ts` glyph set, `tests/packaging.test.ts` `build.files`) are extended, never shrunk; `GLYPH_CHARS` keeps `'0123456789LVEUP!'` as its prefix and APPENDS the 21 missing letters then `. : - + %`.
37. Package version becomes 0.3.0 (tray title `DesMon v0.3.0`, README artifact names, packaging test, F25/F58 literals follow; v2 stays frozen at tag `v2` = 0.2.0).
38. Codex workers own only the graphics file set (`src/renderer/sprites/**`, `src/renderer/{anim,hud,effects}.ts`, `static/{style,menu}.css`, `tests/{sprites,anim,effects,renderer,window}.test.ts`); they never run Electron, git or the network and add no dependencies; every `game.ts` / `src/menu/**` / `static/menu.html` hook-up is a claude task; runtime proof of graphics work is the orchestrator's smoke after merge.
39. Injected clock, no wall time: nothing in `src/core` or `src/server` reads `Date.now`/`performance.now` or sets timers; the engine owns `clockMs` advanced only by `engine.tick(dt)` (non-finite/negative dt → 0; `tick` runs `feverTick` first, then `⌊dt/1000⌋` companion volleys keeping the remainder); the server takes `now()`, `randomUUID()`, `randomBytesHex()`, `randomSeed()` injected (`createApp(deps)`; production passes `Date.now` and `node:crypto`); every timing AC advances time explicitly.
40. Concurrent smokes (up to 3 lanes + the orchestrator) share Electron's single-instance lock, which is scoped by `userData`: when `process.env.SMOKE` is set, `src/main/index.ts` calls `app.setPath("userData", fs.mkdtempSync(path.join(os.tmpdir(), "desmon-smoke-")))` BEFORE `app.requestSingleInstanceLock()` — smokes never collide and never touch the real save or identity file (owned by F43).
41. Wire types (`src/shared/api.ts`) declare their own structural `Companion` so `src/shared` never imports `src/core`; the server imports `ROSTER_CAP`, `SPECIES_IDS`, `resolvePvp`, `mulberry32` from `src/core` and never imports `electron` or `src/main`/`src/renderer` (only `probe.ts` reuses the electron-free `src/main/net.ts`) — one constant set enforces the same caps on both sides.
42. Types: five elements in a fixed cycle (fire → wind → earth → water → dark → fire); a type beats the next two and loses to the previous two; super = ×2, weak = ÷2 (floor 1), same type = normal. Species types are fixed (slime water, bat wind, ghost dark, golem earth, dragon fire); bosses share their species type.
43. Size is a hidden per-species attribute 1–3 (slime/bat 1, ghost 2, golem/dragon 3): draw scale and z-order only; never displayed as a number.
44. The field party is the 5 companions with the highest effective power against the current monster's type, recomputed every volley and every frame (auto-change on spawn); the PvP party is a manual list of ≤ 5 ids stored in the save (`pvpParty`), empty = the 5 strongest by raw power.
45. PvP is two-step and asynchronous: `match` returns the server-picked opponent (rank neighbour or Training Dummy) with its stored PvP party and a match id valid for 120 s; `battle` sends the match id + my party; the server resolves with the deterministic core battle simulation (alternating front-member blows, hp = power × 5, cap 200 blows) and returns the blow list; the client replays it (≤ 12 s) — no re-computation on the client.
46. Only the attacker can steal: on a win, a 15 % roll takes one uniformly random member of the defender's PvP party (not into a full roster). The victim gets a theft record (24 h reclaim window), a native notification on the next poll (every 5 min while online, immediately at boot), and can reclaim from the notification click or the Battle tab; after 24 h (or if the thief no longer holds it) the reclaim fails and the record disappears.
47. Matches are held in server memory (single free instance; a restart expires them: 410 `match_expired` → the client asks for a new match). Thefts live in the `players.thefts` jsonb column (last 8).
48. The overlay is 480×300 (canvas 240×150 at CSS 2×); units draw at 1× (half the v2 size), monsters at their size, bosses at size + 1; the party group overlaps with the largest member at the back.
49. Main may originate exactly one action type (`addCompanion` after a successful reclaim); every other roster change still flows menu → main → game.
50. Version 0.3.0; the v3 server is a second Render web service (`desmon-server-v3`) built from branch `v3`, sharing `desmon-db` (additive idempotent DDL); v2 (tag `v2`) stays deployable from `main`.
51. Module placement of the battle maths: `simulateBattle`, `Blow`, `Battle`, `BATTLE_HP_MULT`, `BATTLE_MAX_BLOWS` live in the new `src/core/battle.ts`; `resolvePvp` and `STEAL_CHANCE` stay in `src/core/collection.ts` (importing `simulateBattle`) — F37's `export function resolvePvp` source pin and the server's import path are kept unchanged (never weaken an existing AC).
52. Effectiveness float colours are one pure helper `floatColor(effectiveness)` in `src/renderer/hud.ts` (`super` → `COLORS.yellow`, `weak` → `COLORS.steel`, `normal` → `COLORS.white`); `game.ts` calls it for `companionAttack` floats and replay blows — keeps the colour rule in the codex-owned graphics set and grep-decidable.
53. Retitled tests (values changed, `it(` never deleted): `tests/collection.test.ts` "activeCompanions picks the 3 strongest, ties by id" → "activeCompanions picks the 5 highest effective powers against the enemy type"; "resolvePvp wins with probability myPower over total and moves one random companion from the loser to the winner" → "resolvePvp wins by the deterministic battle and moves one random defender to the attacker on the steal roll"; `tests/engine.test.ts` "tick fires one volley per 1000ms from the 3 strongest companions and kills chain into the next monster" → "tick fires one volley per 1000ms from the 5 best-matched companions and kills chain into the next monster"; `tests/renderer.test.ts` "a boss draws at scale 3 with a crown and its hp bar raised" → "a boss draws at species size plus one with a crown and its hp bar raised", "active companions draw in a column left of the hero, flipped to face right, star-tinted" → "active companions draw as an overlapping party group left of the hero, flipped to face right, star-tinted"; `tests/sprites.test.ts` "drawBoss paints the species art at scale 3 with the crown centred above it" → "drawBoss scales by species size plus one", "companionSlot stacks three slots upward from the ground left of the hero" → "partySlots stacks back members higher and left of front members with scale by size"; `tests/server/pvp.test.ts` "losing the match moves one of my companions to the opponent and reports it as lost" → "losing the match moves nothing: the attacker never loses a companion and lost is null" — the v3 test-migration policy of GAME_DESIGN_V3 §0.

  module must never crash startup), `uIOhook.stop()` on `will-quit`.
- Automatic graceful fallback to window-focused input (renderer `keydown` /
  `mousedown`, drag strip excluded) whenever the permission is missing or the
  hook fails; fallback listeners detach when global mode activates (F14).
- Real-hook behavior is verified ONLY in the Manual Verification Appendix (M4).
- Injected clock: no `Date.now`/`performance.now`/timers in `src/core` or
  `src/server` logic. Engine time advances only through `engine.tick(dt)`
  (injected dt; the renderer feeds rAF dt clamped to 100 ms): fever windows,
  companion volleys and cooldowns are measured on that clock (Assumption 39).
  The server takes `now()`, `randomUUID()`, `randomBytesHex()` and
  `randomSeed()` injected via `createApp(deps)` (PvP cooldown, rate-limit
  window, ids, seeds); production wires `Date.now` and `node:crypto` in
  `src/server/index.ts` only. `net.ts` takes `fetchFn` injected. Tests
  advance time explicitly; wall-clock time is never observed.
- Theft poller (v3): main's `createTheftWatcher` in `src/main/thefts.ts`
  uses an injected `setInterval` / `clearInterval` pair (production passes the
  globals from `src/main/index.ts`; `tests/thefts.test.ts` passes fake timers
  and a fake session and advances them explicitly); `src/core` and
  `src/server` still never read the clock — the reclaim window is measured on
  the server's injected `now()`, and the menu's `theftRows(thefts, now)`
  takes `now` as an argument. The watcher is never started under `SMOKE=1`.
- Deterministic battle (v3): `simulateBattle` uses no rng at all; `resolvePvp`
  v3 draws exactly twice (steal roll, then victim index — always consumed);
  the server returns the blow list and the client only replays it on its
  presentation clock (`update(dt)`), never re-simulating.
- Injected RNG (`mulberry32(seed)`; `resolvePvp` draws exactly twice; the
  boss capture draw follows the loot draw), injected store (`MemoryStore`)
  and injected `fetch` for the net client — tests never open sockets, never
  reach the network, never touch a real DB. `SMOKE=1` forces the client
  offline by code and isolates `userData` (Assumption 40).

## Non-Goals

- No auto-update mechanism.
- No Windows or Linux builds executed in this run — the electron-builder
  `win`/`nsis` section is config-only (F26); `npm run package` targets macOS
  arm64 only. No code signing or notarization.
- No localization; all text is English.
- No CI pipeline setup in this run.
- Networking exists ONLY in `src/main/net.ts` (client: injected fetch,
  `AbortSignal.timeout(5000)`, never throws, offline by default) and
  `src/server/**` (the Render server), offline-first: renderers and the menu
  never touch the network, tests never touch the external network, `SMOKE=1`
  forces offline. No telemetry, analytics or cloud saves (the leaderboard
  snapshot is name + score + roster only).
- No real-time PvP, no spectating; the replay is a deterministic
  re-enactment of the server's blow list (never a live or re-simulated
  fight); no match history or `matches` table.
- No push infrastructure: theft notifications come from a 5-minute poll
  while the victim is online (immediately at boot); the Battle tab inbox is
  the fallback surface.
- No multi-instance server: pending matches are in-memory on the single free
  instance; a restart expires them (`410 match_expired` → find again).
- The type chart is the fixed 5-cycle; no dual types, no STAB, no status
  effects, no type-specific moves or animations beyond the badge and float
  colours.
- Size is never shown as a number (draw scale and z-order only).
- No accounts beyond nickname + bearer token: no passwords, e-mail, PII,
  nickname uniqueness, moderation or token rotation.
- No anti-cheat (accept-and-rank): leaderboard/PvP stats are self-reported;
  "server-authoritative" covers the PvP verdict and roster bookkeeping only;
  only shape/caps, rate limit, body cap and cooldown bound abuse.
- No paid Render tier, no DB rotation automation (manual runbook in
  `## Deployment`), no CORS (Electron main is the only client).
- No settings UI beyond the tray menu and the Collection & Battle window
  (no preferences window, no volume/mute control, no window-size or scale
  options, no hotkey to open the menu).
- No sound beyond the 4 synthesized WebAudio blips (Assumption 13).
- No balance tuning beyond the stated formulas; no equipment/abilities/trinket
  effects, no idle or offline progression, no achievements, no win/end state
  (rebirth is the only prestige).
- No multi-window features beyond the single overlay + the single menu
  window; single fixed-size overlay.
