## 3. 기능 계약

### A. 신뢰할 수 있는 환생 표시

`src/core/hero.ts`의 실제 준비 판정과 `src/renderer/hud.ts`, `src/menu/hero.ts`가 같은
문턱을 사용하도록 최소 수정한다. `heroRequiredLevel(reincarnations)`만 사용하는 것으로는
충분하지 않다. 이미 열린 구버전 후보의 `offerLevel`, 휴식, 보류, 환생 횟수 상한도 반영한다.

완료 조건:

- 첫 환생 이후12/13, 요구 레벨 상한17/18, 열린 옛 후보, 휴식·보류 종료 직전/직후 검사.
- 준비 전 가득 찬 레벨 막대0건. 휴식·보류 막대는 대기임을 구분하고 레벨 달성으로 표현하지 않는다.
- 최대 환생 상태는 더 달성할 수 있는 목표처럼 표시하지 않는다.
- 기존 E2E `reincarnation-progress-honesty`가 통과하고 나머지 검사가 유지된다.

### B. 발견 요약과 목표

기존 도감 위쪽에 요약을 둔다. 새 탭이나 별도 퀘스트 화면을 만들지 않는다.
문구는 “지난 확인 이후 발견”으로 한다. 실제 발견 시각이 없는 과거 데이터에 날짜나 순서를 만들지 않는다.
요약에는 영웅/몬스터별 수와 일부 카드를 보여주고 전체 도감으로 이어진다.

저장에는 기존 `seenHeroes`/`seenMonsters`와 별도의 확인한 ID 집합, 그리고
`{kind: hero|monster, id}` 목표 하나 또는 없음만 추가한다. 진행률과 적격 여부는 저장하지 않고
기존 `conditionStatus`/`discoveryContext`로 계산한다. 이 상태는 로컬 UI 상태이며 전투 보상은 아니다.

확인 정책은 명시적인 “표시한 발견 확인” 동작이다. 메뉴를 연 것만으로 지우지 않는다.
확인 요청은 실제 표시한 ID 집합만 담으며, 그 사이 생긴 발견은 남아야 한다.
읽음 상태는 멱등하게 합치고 영구 발견을 삭제하지 않는다. 읽지 않아도 불이익은 없다.

목표는 도감 카드에서 무료로 선택·변경·해제한다. 미발견 이름·원색 아트·능력치를 먼저 공개하지 않는다.
조건 충족과 실제 발견/획득은 구분한다. 시간대·장착 조건이 다시 미달해도 목표를 임의 교체하지 않는다.
목표 완료는 발견 상태의 표시로 끝나며 추가 수령 버튼이나 재화는 없다.

완료 조건:

- 구세이브 첫 이관은 기존 발견을 확인한 상태로 기준화한다. 가짜 신규 발견0건.
- 새 게임에서는 이후 실제 발견만 미확인으로 쌓인다. 재시작·환생·메뉴 재개 후 보존한다.
- 화면 표시→추가 발견→이전 확인 요청 순서에서 추가 발견이 지워지지 않는다.
- 확인 ID는 요청 시점의 실제 `seen` 집합에 포함된 것만 합친다. 유효한 종류의 ID여도 아직 미발견이면 확인 처리하지 않는다.
- 중복/오래된 요청은 안전하고, 잘못된 종류·ID·배열은 IPC와 `parseSave`에서 거부/정규화한다.
- 목표 없음·변경·해제·완료, phase 전환, 열린 후보, 실제 미발견 실루엣을 검사한다.
- 5초 상태 갱신에도 펼친 카드·스크롤·키보드 포커스가 유지된다. 저장 실패를 저장 성공으로 알리지 않는다.

### C. 훈련 효과의 정직한 예고

`heroAttackPower` → `trainedHeroPower`의 기존 bigint 계산을 재사용한다.
표시는 **현재 상태의 비치명·비피버 영웅1회 피해**로 한정한다. 파티 DPS나 처치 속도 증가로 표현하지 않는다.
예: `14 → 14 (+0)`, `22 → 23 (+1)`. 현재 레벨·영혼·환생·훈련 단계 변화에 따라 갱신한다.

완료 조건: 예고와 동일 조건의 실제 attack 피해가 일치한다. +0을 숨기지 않는다.
최대 훈련, 골드 부족, 상태 갱신, 연속 클릭을 검증한다. 비용/효과 공식과 구매 토큰 방어는 유지한다.
미끼·재굴림도 기존 설명의 무료 경로와 조건을 유지하며 “쓸모없는 구매”로 단정하지 않는다.

## 4. 초과 포획: 선행 실험과 조건부 출하

세 안을 비교한다. 먼저 게임에 기본 적용하지 않고 주입 엔진 실험에서 검증한다.

| 안 | 동작 | 주요 반례 |
| --- | --- | --- |
| 현재 방식 | 초과 포획 즉시 방출, 누적2회당 영혼1 | 편성 기회 손실 |
| 기존 관리 개선 | 기존 소모/방출 흐름으로 방문 시 공간 확보, 보류 없음 | 공간을 비우려는 관리 의무·기존 동료 손실 |
| 후보1개 보류 | 첫 초과 후보를 고정 보관, 보류 중 추가 포획은 기존 방출 규칙 | 첫 후보가 약하면 뒤의 좋은 후보를 놓침·영혼 지연 |

실험에서는 환생 선택과 동료 관리 간격을 독립 변수로 분리한다. 동료 관리0회/2분/10분을
비교할 때 입력·환생·구매 규칙은 고정한다. 다음 단계에서 환생과 관리를 같은 방문 일정으로 묶어
실제 업무 중 주의 비용을 평가한다. 매 순간 최적 행동을 하는 봇을 방치 사용자로 부르지 않는다.

보류안의 기본 계약은 다음과 같다. 실험 결과에 따라 아래 계약을 바꾸면 새 프로토콜 버전으로 재검토한다.

- 보류 후보는 동료 슬롯이나 자동 파티에 포함하지 않으며 운영 업로드에도 보내지 않는다.
- 기존 보유 동료를 자동 삭제하지 않는다. 수락 시 빈 슬롯 또는 명시적으로 고른 교체 대상이 필요하다.
- 첫 보류 후보는 새 포획으로 자동 교체하지 않는다. 만료가 없고 언제든 기존 방출 보상으로 전환 가능하다.
- 보류 중에는 해당 포획의 영혼을 지급하지 않는다. 거절/보상 전환 때 기존 `releasedCount` 규칙으로1회 정산한다.
- 교체 수락 시 선택한 기존 동료의 처리는 현재 `sacrifice` 규칙을 재사용한다. 확인 화면에 대상의 영구 삭제와 해당 영혼 보상을 표시하며, 희생과 후보 추가를 하나의 원자적 작업으로 처리한다. 보류 후보에는 방출 영혼을 중복 지급하지 않는다.
- 교체 대상이 이미 소모·도난·삭제됐다면 보류는 유지하고 재선택을 요구한다. 다른 대상을 대신 삭제하지 않는다.
- 수락/거절은 요청 토큰과 원자적 저장으로 처리한다. 저장 실패·재시작에도 포획이 복제되거나 사라지면 안 된다.

필수 상태표: 빈 보류, 보류 중 연속3포획, 공간 발생, 교체 대상 부재, 수락/거절, 재전송,
저장 실패, 재시작. 모든 포획은 **보유 / 방출 정산 / 보류** 중 하나이며 최종 정산은1회다.
기존 방출 횟수의 홀짝도 보존한다. 미지급 영혼과 지급 지연을 결과에서 제외하지 않는다.

**사전 채택 기준**은 [평가 프로토콜](EVALUATION_PROTOCOL.json)에 고정한다.
강제 창·기존 동료 자동 삭제·중복 정산·재로드 손실은 모두0이어야 한다.
비교 대상은 **같은10분 방문 일정의 `existing-management-only`**로 고정한다.
100개 seed 각각의5속성 파티 공격력 합이 모두 기준 이상이고 적어도 한 seed·속성에서 개선되며,
후보 손실과 클릭 수도 각 seed에서 기준 이하일 때만 구현을 검토한다. 개선·악화 seed 수와
5속성별 차이의 p10/p50/p90를 모두 보고한다. 방문 시 대상 선택·공간 확보 규칙과 클릭 수 계산은
V06-01에서 실행 전 확정하며 두 안에 공통 적용한다. 2분 관리에서만 좋아지면 방치 개선으로 채택하지 않는다.
영혼 지연이나 다른 교환 비용이 커지는 안은 자동 채택하지 않고 결과와 사용자 관찰을 검토한다.
기준을 통과하지 않으면 **v0.6에서 포획 상태 변경을 제외**하고 필수 UI 개선으로 출시 후보를 만든다.
창고 용량 확대나 보상 상향으로 실패를 덮지 않는다.

## 6. 측정과 테스트 계획

실행 전 [프로토콜](EVALUATION_PROTOCOL.json)에 seed1..100, 시작 세이브 해시, 입력 시간표,
환생·구매·관리 정책을 기록한다. 결과에 맞춰 기준을 바꾸지 않는다. 변경이 필요하면 이유와
새 프로토콜 버전을 남기고 이전 결과를 보존한다.

기존 `measure.mjs`의 canonical9조합과 무료/훈련/미끼/재굴림 비교는 유지한다.
추가 실험은 별도 구역에 원시 표본·설정·분포를 담고 해시로 연결한다. 감사는 그 분포도
원시 값에서 재계산한다. 현재 없는 CLI 옵션을 이미 실행 가능한 명령처럼 문서화하지 않는다.

주요 측정:

- 첫 보상·포획·환생 기회, 최장 무처치·무발견·의미 이벤트 공백의 p10/p50/p90·최대·미도달.
- 포획 시도/보유/방출/보류 수, 후보 손실, 미지급 영혼, 방문·클릭 수.
- 상대5속성별 `activeCompanions`와 기존 영웅 버프/`effectivePower`의 공격력 합.
  이는 공격 주기와 실제 PvP 판정 전체를 대체하는 지표가 아니다. 기본 전투력 하나로 우월성을 판단하지 않는다.
- 골드 수입·지출·잔액 최저점·구매 불가 시간, 같은 seed별 정책 차이.
- 피버: 매분120입력의 균등2Hz와20입력 묶음6회. 총입력·seed·다른 정책은 동일하게 고정한다.

순수 신규 방치는 동료0·입력0·메뉴0으로 분리한다. 진행0은 현재 설계의 대조 결과이며
자동 성장 통과 사례가 아니다. warm-idle은120초 활동 후 입력0이며 동료 미획득 표본도 남긴다.

실제 Electron은5/15/30분 × active/idle/intermittent를 **동일 데스크탑에서 순차 실행**한다.
순수 관측150분, 빌드·부팅·진단 포함160~180분의 실행 슬롯을 확보한다. v0.5와 실제시간 전후 비교까지
하려면 기준선에도 같은9조합이 필요하므로 총320~360분을 예상한다. 기존 실제5분만으로 전후9조합을 주장하지 않는다.

계획 시 `e2e.mjs`와 `audit.mjs`는 파일 하나를 다뤘다. V06-01에서9결과의 manifest/집계와 검증을 추가했다.
각 원본의 소스 지문·해시·실제 시간·고유 duration/profile을 검사하고 실패/누락을 숨기지 않는다.
기존 단일 실행도 지원한다. 30분 관측의 중간 체크포인트를 독립5분/15분 실행으로 바꾸어 부르지 않는다.
UI 기능 검사는 자연 시작 후의 명시적 fixture이며 자연 획득 기록과 구분한다.

새 E2E에는 HUD 경계, 신규/구세이브 요약, 확인 중 추가 발견, 목표 변경/해제/완료,
훈련 예고/중복 구매, 재시작, 채택 시 연속 포획·대상 삭제·정산을 추가한다.
기존 무메뉴 실시간 정책은 유지하고, 새 기능을 선택하는 행동은 별도 scripted journey로 기록한다.

개발 중 단위 검사는 관련 기존 파일을 대상으로 실행한다. 변경마다 완료 판단 전에 아래 게이트를 실행한다.

```sh
npm test && npm run lint && npm run typecheck
```

통합 시 실행 가능한 기존 명령:

```sh
node .harness/v5/loop/fun.mjs selftest
node .harness/v5/loop/e2e.mjs .agentdoc/v06-run/e2e-5-active.json 5 active
node .harness/v5/loop/measure.mjs .agentdoc/v06-run/measure.json --seeds 100 --seed 1 --policies
npm run smoke
npm run package
```

현재 실행은 [LOOP.md](LOOP.md)의 확정된 `e2e-matrix.mjs run` 명령으로9개를 순차 수행한다. 이 절의 명령은 절차이며 완료 결과는 아래 실행 근거와 ACCEPTANCE.md를 따른다.

## 7. 재미 검증과 출시 완료 조건

사람 관찰은 탐색적으로5명×30분을 제안한다. 한 세션 안의5/15/30분에서
기대했던 결과, 도움 없이 설명한 목표, 자발적으로 다시 본 이유, 원래 작업 복귀와 중단 요청을 기록한다.
참가자별 허용 업무 방해를 시작 전에 정한다. 관찰 양식은
[기존 장르팩 양식](../../.harness/v5/genre-packs/desktop-companion-clicker/playtest-observation.md)을 재사용한다.

보이는 것이다. 소수 탐색 결과이므로 일반적인 재미·유지율 검증으로 표현하지 않는다.
참가자가 없으면 사람 검증은 `PENDING`으로 남긴다. 자동 검사로 채워 넣지 않는다.

- [x] 실제 E2E9조합 및 새 UI journey 통과. 누락이 있으면 기술 검증·출시 완료로 체크하지 않고 미완료 후보로 인계.

보류 후보는 로컬 전용이므로 수락하기 전 서버 로스터/PvP에 나타나지 않아야 한다.

기존 npm 명령 이름과 `.harness/CURRENT=v3`는 유지한다. 앱v0.6과 리뷰 도구v5는 별개의 버전이다.
하네스 출력 형식을 확장할 때는 그 스키마와 회귀 검사를 갱신하며 v3 Ralph lane 도구를 임의로 교체하지 않는다.
코드 롤백 시 신형 저장 필드가 구버전에서 버려질 수 있으므로 테스트/출하 전 세이브 백업으로 복구한다.
특히 조건부 보류 후보는 구버전 다운그레이드에서 자동 보존된다고 약속하지 않는다.
