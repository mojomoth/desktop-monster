## 2. 기준선 보존과 개발 루프 구성

먼저 `git status`, 현재 버전, 필요한 도구와 의존성, 소스 지문을 확인하라.
이 저장소에는 이전 작업의 수정·미추적 파일이 많다. `git HEAD`만으로 기준선을 대신하거나
reset/clean/checkout으로 작업을 없애지 마라. 변경할 파일은 수정 전 내용과 해시를 별도 보관하고,
기존 변경과 이번 변경을 추적할 수 있게 하라. 개인 세이브·인증정보를 실행 근거에 복사하지 마라.

새 `.agentdoc/v06-<실제 시작 시각>/`를 만들고 다음을 기록하라.

- `baseline/`: 시작 상태, 소스 지문, 필요한 파일 스냅샷, 최초 게이트 결과.
- `loop.json`: 작업 ID, 상태, 의존성, 담당자, 소유 파일, 시도 기록, 검증 근거, 다음 작업.
- `sessions/iter-NN.md`: 변경 이유, 명령·종료 코드·로그 경로, 발견한 문제, 다음 행동.
- `evidence/`, `reviews/`: 원시 측정, E2E 결과와 스크린샷, 역할별 요청·응답과 감사 기록.

`docs/v0.6/LOOP.md`에 실제 실행·재개 절차와 파일 소유권을 문서화하라.
기존 v5 실행기를 재사용해 최소한의 실행 가능한 루프를 구성하라. 필요한 task 상태/재개 기능이
없으면 작은 Node 실행기로 추가하고 검사하라. 새 프레임워크나 의존성은 도입하지 마라.
기존 `fun.mjs`의 구현 리뷰와 `audit.mjs`의 분석 완료만으로 개발 작업 완료를 대체할 수는 없다.

루프는 다음 순서로 동작해야 한다.

`의존성 충족 작업 선택 → 파일 소유권 배정 → 구현 → 관련 검사 → 통합 게이트 → 검토 → 완료 기록 → 다음 작업`

작업 상태는 `pending / running / verified / excluded / blocked`로 구분하라.
`verified`에는 해당 구현을 검사한 명령, 성공 종료 코드, AC 근거와 소스 지문이 필요하다.
`excluded`는 계획에서 조건부로 지정한 작업에만 적용하고 결정 근거를 연결하라.
오래된 근거·실패한 검사·선행 작업 미완료로 완료 상태를 만들 수 없게 하라.
저널은 호스트 하나만 수정하고 원자적으로 저장하라. 잘못된 상태 전이와 재개를 검사하라.
작업별 `verified`는 당시의 검증 이력으로 보존하고 이후 수정의 영향을 받은 작업을 재검증하라.
매 변경마다 모든 작업을 초기화하지 마라. 최종 V06-09의 전체 검증은 반드시 최종 지문에서 수행하라.

컨텍스트가 줄거나 세션이 재개되면 새 계획을 만들지 말고 `LOOP.md`, `loop.json`, 마지막 기록부터 읽어라.
실행 중 프로세스와 결과를 확인해 장시간 E2E를 중복 실행하지 마라.
복구할 수 없는 미완료 실행은 보존하고 해당 조합을 다시 실행하라.

V06-01의 기준선·실험 조건 고정 부분은 게임 소스를 수정하기 전에 마쳐라.
방문 시 대상 선택·공간 확보·클릭 수 계산과 시작 세이브를 먼저 구체화하고 해시로 고정하라.
그 뒤 계획의 의존성에 따라 01의 도구 구현과 02/03 등을 병렬화하라.
필요한 기준선 재현은 보관된 동일 소스에서 수행하고 수정 중인 소스와 섞지 마라.

## 3. 멀티에이전트 운영

실제 서로 다른 에이전트로 아래 네 역할을 수행하라. 한 에이전트가 이름만 바꿔 네 응답을 만들지 마라.
이전 세션의 agent ID와 응답은 과거 근거이며 이번 검토의 독립성을 증명하지 않는다.
호스트가 직접 앱을 관찰한다면 Playtester를 맡고 Designer·Critic·Balance를 별도로 실행해도 된다.
동시 실행 슬롯 수를 지키고, 모델은 호스트 기본값을 사용하라.

| 역할 | 책임 |
| --- | --- |
| Designer | 계획의 사용자 경험과 재미 가설을 구현에 연결하고, 필요한 대안을 제안 |
| Critic | 가짜 선택, 우월 전략, 무의미한 반복, 모순된 안내, 관리 의무와 업무 방해를 반례로 검토 |
| Balance | 실제 엔진의 공식·seed별 원시 결과·재화 보존·분포·주의 정책과 채택 기준 검증 |
| Playtester | 실제 Electron 화면과 입력→IPC→저장→재개를 확인하고 기능·논리·행동 근거 종합 |

독립 코드 읽기와 측정 준비는 병렬화하되, 판단은 **Designer → Critic → Balance → Playtester** 순서로 연결하라.
각 역할은 앞선 제안에 동의·반박하는 이유와 근거를 남겨야 한다.
구현 담당자에게는 작업 ID와 소유 파일을 지정하라. 같은 파일을 동시에 수정하지 마라.
특히 engine/save/IPC, `src/menu/index.ts`, `tests/menu.test.ts`는 담당을 조정하라.
최종 감사는 `audit.mjs`가 발급한 실제 prompt/template과 `next/submit/report` 절차를 사용하라.

계획에 이미 결정된 범위를 매 반복마다 새로 확대하지 마라. 범위 안의 blocker/major는 수정 후 재검증하고,
다음 버전 제안과 사람 관찰이 필요한 가설은 분리해서 기록하라.

## 4. 구현 범위와 놓치면 안 되는 계약

세부 AC와 작업 순서는 `DEVELOPMENT_PLAN.md`의 V06-01~10을 따른다.
진행 상태는 해당 문서와 저널에 반영하되, 실제 검사를 통과하기 전에 체크하지 마라.

- **환생 안내:** 실제 준비 판정과 막대·문구를 일치시켜라. 첫 환생 이후 문턱뿐 아니라
  이미 열린 구버전 후보의 `offerLevel`, 휴식·보류, 환생 상한을 함께 처리하라.
- **발견 요약:** 기존 도감에 추가하고 영구 발견과 확인한 ID를 분리하라.
  구세이브의 기존 발견은 읽은 상태로 이관하고, 명시적으로 표시된 발견을 확인하는 동작을 사용하라.
  요청 사이에 생긴 발견을 지우거나 아직 발견하지 않은 ID를 미리 확인 처리하지 마라.
- **목표:** 무료로 하나를 선택·변경·해제하며 기존 조건 계산을 재사용하라.
  적격과 발견/획득을 구분하고 미발견 정보는 보호하라. 조건이 다시 미달해도 목표를 임의 변경하지 마라.
  메뉴 갱신 중 펼친 카드·스크롤·키보드 포커스를 보존하고 저장 실패를 성공으로 알리지 마라.
- **훈련 예고:** 기존 bigint 공식으로 현재 상태의 비치명·비피버 영웅 1회 피해를 보여라.
  `14 → 14 (+0)`처럼 실제 정수 효과를 드러내고 가격이나 공식은 바꾸지 마라.
- **측정:** 초과 포획 3안과 관리 간격, 동일 총입력량의 균등/폭주 피버 실험을 구현하라.
  별도로 손으로 쓴 유사 게임 모델을 실제 엔진 결과라고 제시하지 마라.

초과 포획 보류는 실험 전에 기본 기능으로 구현하지 마라. 비교 대상은 같은 10분 방문 일정의
`existing-management-only`다. 프로토콜의 seed별·5속성별 조건, 후보 손실·클릭 수와
영혼 지연 등 교환 비용을 모두 검토하라. 평균만 좋아졌다고 채택하지 마라.

채택 근거가 부족하거나 해결되지 않은 교환 비용 때문에 사람 관찰이 필요하면,
근거를 `EXPERIMENT_RESULTS.md`에 남기고 V06-07/08을 **조건부 제외**한 뒤 필수 기능을 마무리하라.
V06-06의 실제 실험은 필수다. 실행하지 않은 실험을 실패로 간주해 조건부 제외로 처리하지 마라.
채택 기준을 낮추거나 테스트를 약화해 기능을 억지로 포함하지 마라.
채택 시에는 첫 후보 유지·자동 삭제 없음·한 번만 정산·명시적 교체·stale 대상 보호·저장 실패/재시작
복구·수락 전 서버 로스터 제외 계약을 모두 구현하고 검증하라.

## 5. 검증과 장시간 실행

각 작업의 관련 AC를 실제 실행하고, 작업을 완료로 기록하기 전에 아래 게이트를 그대로 실행하라.
공유 작업 트리에서 게이트를 실행하는 동안에는 다른 에이전트의 수정을 멈추고 검사 대상 지문을 고정하라.

```sh
npm test && npm run lint && npm run typecheck
```

테스트 삭제·skip·완화, 엄격도 하향, 실패를 숨기는 셸 처리는 금지한다.
시간/RNG/입력을 주입하는 결정적 검사를 사용하고 실사용 세이브는 건드리지 마라.
이미 설치된 도구를 먼저 쓰고 의존성이 없을 때만 lockfile 기준 `npm ci`로 복구하라.

현재 존재하는 실행 명령은 다음과 같다. 아래 `v06-run`은 실제 세션 경로로 바꿔라.

```sh
node .harness/v5/loop/fun.mjs selftest
npm run build
node .harness/v5/loop/measure.mjs .agentdoc/v06-run/evidence/measure.json --seeds 100 --seed 1 --policies
node .harness/v5/loop/e2e.mjs .agentdoc/v06-run/evidence/e2e-5-active.json 5 active
npm run smoke
npm run package
```

위 E2E 명령은 9개 중 한 조합이다. V06-01에서 `e2e-matrix.mjs`와 9결과 감사 집계를 구현하고,
실제로 존재하는 CLI와 사용법을 문서화한 다음 사용하라. 기존 단일 E2E 감사도 유지하라.
집계는 9개 원본·스크린샷 해시·동일 소스·실제 경과 시간·조합 중복/누락·실패를 검증해야 한다.
측정 분포는 원시 표본에서 재계산하고 설정이 다른 seed 결과를 짝지어 비교하지 마라.
하네스 자체 변경도 테스트하고 사용한 실행기·프로토콜의 해시를 남겨라.

최종 실제 플레이는 **5/15/30분 × active/idle/intermittent = 9개 독립 실행**이다.
동일 데스크탑에서 순차 실행하며 관측만 총 150분, 준비와 진단을 포함하면 대략 160~180분이 필요하다.
시간 가속, 엔진 시뮬레이션, 30분 실행 안의 체크포인트로 별도 5분/15분 실행을 대체하지 마라.
기능용 0분 실행은 개발 중 빠른 검사에만 사용하라.

네이티브 E2E는 프로덕션 창·preload·renderer·IPC·저장을 이용하고 격리된 userData와 합성 입력을 사용하라.
실제 전역 입력 훅이나 개인 저장 파일을 사용하지 마라. 네이티브 접근성 권한을 자동 부여하려고 하지 마라.
기존 무메뉴 관측 정책을 기록하고, 발견 확인·목표·훈련 등 새 UI 조작은 별도 journey로 검사하라.
전체 main 시작 경로는 별도 smoke로 검증하라.

순수 신규 idle과 120초 활동 후 warm-idle을 구분하고 미도달/진행 0 표본도 남겨라.
기존 측정의 즉시 환생 선택과 네이티브 무선택 정책을 동일 조건으로 취급하지 마라.
과거 5분 실행을 실행하지 않은 15/30분 기준선으로 확장하거나 서로 다른 정책의 차이를 개선 효과로 주장하지 마라.

V06-09에서 **package.json/lock의 버전을 먼저 0.6.0으로 고정**하고 최종 소스를 동결하라.
그 소스에서 canonical 100 seed 측정, 채택 근거 실험, 저장소·하네스 게이트,
실제 E2E 9개와 새 UI journey, 네 역할 감사를 모두 다시 실행하라.
과거의 744개 테스트·17개 하네스 검사·smoke 결과는 이번 통과 근거가 아니다.
수정이 발생하면 이전 근거는 보존하되 stale로 표시하고 최종 지문에 맞는 검증을 다시 확보하라.
최종 장시간 검증 중에는 소유 파일 변경을 동결해 재실행을 줄여라.

장시간 프로세스는 진행 상태를 확인할 수 있는 세션으로 실행하고 약 60초 이내 간격으로
현재 조합·경과 시간·실패 여부를 간단히 알려라. 오래 걸린다는 이유로 검증을 생략하거나
실제로 계속 실행할 수 없는 상태에서 백그라운드로 마무리하겠다고 약속하지 마라.

## 6. 완료 판정과 인계

V06-10에서는 **검증한 같은 버전**을 패키징하라. 감사 뒤 버전을 다시 변경하지 마라.
`release/`의 `.app`과 `.dmg` 생성뿐 아니라 패키지 실행·저장·재개도 격리된 세이브로 확인하라.
구세이브의 골드·동료·영웅·전적과 새 UI 상태, 채택했다면 보류 후보까지 보존되는지 검사하라.
다운그레이드에서 새 저장 필드가 보존된다고 가정하지 말고 백업·복구 방법을 인계하라.

다음 세 상태를 분리하라.

- **구현 완료:** 모든 필수 작업과 채택한 조건부 작업의 AC·게이트가 통과함.
- **기술 검증을 마친 출시 후보:** 위 조건에 최종 동일 소스의 측정·9개 실제 E2E·UI journey·4역 감사·smoke·패키지 검증까지 충족함.
- **사람 재미 가설 검증:** 실제 사람 관찰이 있을 때만 결과를 기록함. 없으면 `PENDING`.

`audit_complete`는 분석 완료이므로 E2E 실패가 있어도 나올 수 있다. 그 상태만으로 출시 후보를 완료 처리하지 마라.
필수 실제 E2E가 하나라도 없거나 실패하면 기술 검증 완료가 아니며, 미완료 후보로 기록하라.
사람이 없다는 이유로 로컬 구현과 기술 검증을 멈추지는 마라.
사람 관찰은 계획의 5명×30분 탐색 기준을 사용하며 대리 지표나 AI 의견으로 채우지 마라.
관찰을 해도 일반적인 재미 향상·유지율 상승이 증명됐다고 주장하지 마라.

실패하면 원인을 조사하고 수정·검사를 반복하라. 환경 문제는 서로 다른 합리적 해결을 시도한
근거를 남기고, 해결 불가능한 의존성만 `blocked`로 기록하라. 단순한 테스트 실패나 긴 실행 시간은 중단 사유가 아니다.
외부 입력이 필수인 작업만 분리하고 가능한 나머지 작업은 끝내라. 누락을 `verified`나 조건부 `excluded`로 숨기지 마라.

마지막으로 다음 산출물을 실제 결과로 갱신하라.

- `docs/v0.6/DEVELOPMENT_PLAN.md`: V06-01~10 상태와 근거.
- `docs/v0.6/LOOP.md`: 구성한 실행 루프, 담당·재개 방법과 실제 명령.
- `docs/v0.6/EVALUATION_PROTOCOL.json`: 실행 전에 고정한 조건과 변경 이력.
- `docs/v0.6/EXPERIMENT_RESULTS.md`: 포획·피버 비교, 원시 결과 링크, 채택/제외 결정.
- `docs/v0.6/ACCEPTANCE.md`: 요구사항별 통과/실패/미확인과 최신 검증 근거.
- `docs/v0.6/HANDOFF.md`: 버전·지문·변경 내용·패키지 경로·호환성·알려진 제한·다음 실험.

운영 배포를 하지 않았으므로 인계에 `DESMON_SKIP_NET=1`과 사유를 적어라.
실제 접근성·전역 입력·운영 PvP 등 실행하지 않은 검사는 별도로 명시하라.
최종 답변은 구현한 내용, 조건부 기능 결정, 실제 검증 결과, 패키지·인계 링크,
사람 검증 상태를 한국어로 간결하게 보고하라. 미완료가 있다면 정확한 원인과 재개 명령을 제공하라.

지금 자료를 읽고 기준선을 보존한 뒤 개발 루프 구성과 구현을 시작하라.
