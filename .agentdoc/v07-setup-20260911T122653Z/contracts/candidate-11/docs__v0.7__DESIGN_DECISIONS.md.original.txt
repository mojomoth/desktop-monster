# DesMon v0.7 설계 결정 — round04 사전등록

이 문서는 V07-01의 현재 round04 설계 계약이다. round03의 세 HP tail 후보는 모두 첫 환생 선별을 통과했지만 실제 12시간 최종 `h70` 자격 목표에 실패했고 채택안은 없다. tail105는 후기 처치와 선택을 회복했으나 자격 도달은 5/20으로 전체 p50이 미도달이었다. round04는 첫 여정과 콘텐츠 조건을 유지하면서 깊은 필드 HP의 성장률을 더 완화하는 새 가설이다. 실행할 실험 ID, 전체 매개변수, 동결 시각은 [EVALUATION_PROTOCOL.json](EVALUATION_PROTOCOL.json)의 `schemaVersion: 2`, `progressionParameterVersion: 2`, `round: 4`, `frozenAt: 2026-09-12T05:05:47.874315+00:00`에 등록되어 있다. 문서 작성은 정식 Designer 검토 응답을 대신하지 않는다.

직전 설계 문서는 [candidate-10 원본](../../.agentdoc/v07-setup-20260911T122653Z/contracts/candidate-10/docs__v0.7__DESIGN_DECISIONS.md.original.txt)에, 직전 프로토콜은 [round03 사전등록 원본](../../.agentdoc/v07-setup-20260911T122653Z/evidence/exploration/round-03/protocol.preregistered.json)에 보존한다. round01/02 원본과 완료된 이전 역할 검토도 그대로 유지한다. 기존 실패·측정·검증 이력을 새 round의 성공 근거로 재인증하지 않는다.

## 1. 목표와 첫 여정

기준 정책은 신규 저장, 100ms tick, 균등 2입력/초, 골드 미사용, 동료 무관리, 준비 즉시 첫 환생 후보 선택이다. 첫 영웅 환생의 성공 p50은 45–60분, 전체 검증 100개 중 최소 90개는 90분 안에 성공해야 한다. 마지막 named 콘텐츠의 자격 충족 p50은 8–12시간이다. 사람의 재미·업무 방해·외형 선호는 별도 관찰 전까지 `humanChecks=PENDING`이다.

첫 환생 전에도 첫 처치·보상·레벨·포획과 다음 환생 레벨을 확인할 수 있어야 한다. 종별 처치 목표, 동료 확보, 원소와 영웅 선택이 다음 목표로 이어지게 한다. 숫자 증가나 반복 스택은 새 콘텐츠 해금으로 세지 않는다. 새 강제 시간 제한을 추가하지 않으며 기존 환생 휴식 120초와 무료 보류 30초는 유지한다. 준비·후보 제시·선택 성공은 각각 기록한다.

## 2. round04 대조와 성장 후보

현재 등록은 레벨만 바꾼 대조 5개와 Lv17·XP1.41의 필드 HP 후보 3개다. 세 후보는 index79까지 기존 필드 HP를 유지하고 이후의 성장률만 1040/1000, 1035/1000, 1030/1000으로 비교한다. 대조도 동일한 v0.7 기능 수정과 아래 콘텐츠 조건을 사용한다. round02 XP141과 round03 세 후보의 첫 성공 전체 p50은 2,902.6초, 90분 성공은 18/20이었다. round03은 원본 첫 사건 대응도 후보마다 20/20 일치했지만, round04의 새 실행을 대신하지 않는다. 첫 여정의 비교 원본, 장기 실패와 변경 전 v0.6 기준선을 각각 보존하고 과거 성공 시각을 새 후보 결과로 옮기지 않는다.

공통 식에서 `L`은 최소 영웅 환생 레벨, `r`은 누적 영웅 환생 횟수, `i`는 0부터 시작하는 몬스터 깊이, `level`은 현재 영웅 레벨이다.

- 환생 요구 레벨: `L + min(6, floor((r + 1) / 2))`.
- 다음 레벨 XP: `floor(20 * xpGrowth ** (level - 1))`. 대조의 `xpGrowth`는 1.4, 세 후보는 모두 1.41이다.
- 처치 XP: `5 + 3 * i`, 보스는 5배. 보스 주기는 8번째마다이며 HP와 골드 보상도 기존 5배를 유지한다.
- 기본 필드 HP는 `115/100`, 후보의 깊은 구간은 아래 정확한 유리수 식을 사용한다. 보스는 일반 HP의 최종 정수 나눗셈 후 기존 5배다. 동료 힘의 기반 HP는 모든 깊이에서 `115/100`을 유지한다.
- 포획 확률: 보스마다 35%, `firstCaptureBossIndex: null`로 최초 포획 보장은 없다. 보스 포획 RNG를 항상 한 번 소비하는 순서를 유지한다.
- 기존 환생 휴식 `120000ms`와 무료 보류 `30000ms`를 유지한다. 새 강제 시간 제한은 없다.

각 실험은 기존 17개 값에 `fieldHpTailStartIndex`, `fieldHpTailNumerator`, `fieldHpTailDenominator`를 더한 20개 매개변수 전체를 사용한다. 새 현재 계약은 `progressionParameterVersion: 2`로 엄격히 검사한다. 보존된 round01/02의 17개 값은 당시 계약의 역사적 검증에만 사용하고 새 실행의 필드 누락을 허용하는 근거로 쓰지 않는다. 후보끼리는 tail 분자만 다르다. `control-l17`과 후보는 XP 성장률도 다르므로 이 대조 차이를 HP만의 효과로 해석하지 않는다. HP 완화의 비교 원본은 보존된 round02 XP141과 round03의 실제 tail 결과이며, 새 실행은 각자의 현재 소스·컴파일·평가·프로토콜 지문에 연결한다.

일반 분모를 포함한 정확식에서 `N/D`는 기본 필드 비율, `T/U`는 tail 비율, `s`는 tail 시작 index다. `s === null`이면 `a = i`, `b = 0`; 그 외에는 `a = min(i, s)`, `b = i - a`다.

```text
일반 필드 HP(i) = floor((10 × N^a × T^b) / (D^a × U^b))
보스 필드 HP(i) = 일반 필드 HP(i) × bossHpMultiplier
```

분자·분모의 거듭제곱과 곱을 bigint로 모두 계산한 뒤 나눗셈을 단 한 번 수행한다. index79의 HP를 먼저 floor한 뒤 tail을 곱하거나 구간마다 반올림하지 않는다. 이번 후보는 `N=115, D=100, s=79, U=1000`이고 `T`는 각각 1040, 1035, 1030이다. index79까지 완전히 같고 index80부터 달라진다. 대조의 `s=null`은 모든 깊이에서 기존 식과 같다. 공통 유리수 tail 식은 round03 V07-05에서 이미 구현했고 71/72/78/79/80/81/5000 경계, 서로 다른 분모, 비활성 tail과 기존 동료 힘 보존을 검사했다. 당시 전체 922개 테스트·lint·typecheck 성공은 보존된 구현 근거이며 round04 후보 성능의 증거가 아니다. 같은 공식을 재구축하지 않고 새 등록값과 실제 export의 결합·후보별 검사·새 측정을 수행한다.

예를 들어 index202의 일반 필드 HP는 tail105에서 252,007,330이며 새 tail1040/1035/1030에서는 각각 77,665,853 / 42,933,116 / 23,665,082다. 이는 정확식 산술로서 깊은 여정 완화의 크기를 보여줄 뿐, 해금 시간이나 통과를 예측한 측정값이 아니다.

XP141/Lv17의 첫 여정은 기존 보상식상 72회 처치(index71 보스까지)로 환생 자격에 도달한다. 동일 초기 저장·정책·탐색 seed에서 첫 환생 이전의 처치/보상/레벨/포획, 준비·제시·선택 시각과 선택 ID가 round02 XP141 원본과 일치하는지 새 후보별로 확인한다. 경계 이후만 바뀐다는 계산만으로 선별을 통과 처리하지 않는다. 같은 20개 seed의 실제 120분 선별을 다시 실행해야 한다.

tail이 완만해져도 로스터 30명과 무관리 정책은 그대로다. 정원이 차면 새 강한 동료도 방출되는 구조를 이번에 바꾸지 않는다. 동료의 기반 HP가 기존 115/100을 유지하므로 새로 포획 가능한 깊이와 필드에 대한 상대적 힘이 크게 달라질 수 있다. 빠른 보스 처치가 더 강한 동료 확보로 이어져 후기가 과속할 수도 있고, 정원이 빨리 차서 특정 초기 파티에 계속 묶일 수도 있다. 후보별 처치·포획·파티 힘·동료 수·환생·최장 처치/의미 있는 변화/발견 공백과 2/4/8/10/12시간 경과를 함께 보고한다. 첫 목표 통과나 `h70` 자격 도달만으로 긴 정체를 감추지 않는다. 후보 중 어느 것도 현재 성공 또는 채택으로 선언하지 않는다.

새 요구 레벨의 상단은 `L + 6`이며 과거의 고정 12–18 clamp를 새 후보에 재사용하지 않는다. 이미 열린 레거시 3개 후보와 제시 당시 요구 레벨을 보존한다. 새 후보 제시·재굴림에는 현 실험 요구 레벨을 적용한다. 카탈로그 ID·롤·중복 원소 등 기존 유효성 검사는 유지하며 조건 변경만으로 유효한 열린 제안을 버리지 않는다.

실제 엔진에서 사용한 20개 매개변수를 core export와 측정 원본에 연결한다. 등록 프로토콜과 실제 런타임 매개변수가 일치하지 않으면 그 실험을 유효한 비교로 받지 않는다. 하네스에서 성장 식을 다시 구현하거나 환경변수만 바꾼 것으로 적용을 추정하지 않는다. Host는 V07-01의 새 검증 전에 제품 export를 tail 비활성 `control-l17`과 일치시킨다. V07-01은 새 수치 계약과 설계의 검토이며, 후속 V07-05는 이미 구현된 공통 tail 식에 새 후보값을 적용하고 검증·측정한다. 이는 비교 시작점 설정이며 채택이 아니다. `selectedExperiment`는 `null`이다. 선택은 두 목표를 통과한 실제 비교 결과로 기록하며 목표 검증이나 출시 완료를 대신하지 않는다.

### round03 실제 결과와 round04의 근거

공식 [round03 탐색 원본](../../.agentdoc/v07-setup-20260911T122653Z/evidence/exploration/round-03)에는 8개 실험의 완료된 120분 선별과 세 tail 후보의 완료된 12시간 보고서·execution 기록이 있다. Lv16–20 대조 5개는 새 선별에서도 실패하여 12시간은 `NOT_EVALUATED`다. 세 tail 후보는 각각 첫 성공 전체 p50 2,902.6초·90분 성공 18/20으로 선별을 통과했고, 등록된 첫 사건 대응 검사는 후보별 20/20 일치했다. 그러나 세 후보 모두 실제 최종 자격 목표는 `FAIL`이며 채택안은 없다. 검증 seed 1–100은 사용하지 않았다.

추가 처치는 표본별 12시간 값에서 같은 표본의 8시간 값을 뺀 뒤 집계한다. 서로 다른 시점의 전체 p50끼리 뺀 값으로 대신하지 않는다. tail105의 추가 처치 범위는 644–44,543회였다. `h70` 자격 도달 시각은 18,742.8 / 27,292 / 37,073 / 37,590.5 / 39,203.5초로, 2개는 8시간보다 빨랐고 15개는 12시간에도 미도달이다. 성공한 5개만의 p50 37,073초(약 10.30시간)는 전체 p50 `null`을 대체하지 않으며 목표를 통과시키지 않는다.

후기 활동의 회복과 새 콘텐츠 경험은 분리한다. tail105의 `h58` 자격/제시/선택은 20/20·20/20·0/20, `h62`는 14/20·13/20·0/20이었다. `starvoid` 자격/등장/처치는 각각 10/20이다. 기준 정책의 첫 슬롯은 일반 영웅을 선택하고 희귀 영웅은 세 번째 슬롯에 오므로, 희귀 자격·제시 증가를 실제 선택 증가로 기록하지 않는다. 같은 기준 정책을 유지하고 희귀 카드의 실제 선택 UI는 별도 시나리오에서 확인한다.

처음 등장·제시를 나타내는 records를 2시간 이후부터 12시간 종료까지 잘라 양쪽 관측 경계를 포함해 계산한 최장 발견 공백 p50은 tail111 21,062.9초, tail108 13,497초, tail105 6,274.5초다. tail105에서도 최악은 24,353.8초였다. 이 값은 전체 여정의 누적 checkpoint 최장값이나 실제 선택/처치에 따른 새 도감 획득 공백과 의미를 구분한다. 예를 들어 tail105 seed10004는 일반 영웅 50종을 14,286.2초에 소진한 뒤 12시간까지 새 획득 공백 28,913.8초가 있었지만, 8시간 이후에도 영웅 환생을 120번 선택했다. 이 표본의 긴 발견 공백은 전투 정체와 같지 않으며 카탈로그 소진과 첫 슬롯 정책의 영향이다. 반대로 낮은 파티의 느린 처치·선택은 실제 후기 활동 지표로 계속 보고한다.

따라서 round04는 콘텐츠 조건을 낮추거나 선택 정책을 바꾸지 않고, 깊은 HP만 추가 완화해 중간·느린 표본의 자격 도달을 비교한다. 이미 빠른 표본이 더 일찍 해금하고 일반 영웅을 조기 소진할 위험도 함께 관측한다. 두 목표의 전체 표본 판정, 표본별 후기 처치 증가·선택, 자격·등장·선택 및 발견 공백을 함께 본 뒤 다음 설계를 판단한다. 현재 세 후보 어느 것도 통과 또는 채택으로 선언하지 않는다.

## 4. 획득·동료 관리·PvP UI 계약

### 동료 레벨과 환생

동료 레벨은 양의 안전 정수 `number`로 유지하고 게임상 Lv10 상한을 제거한다. 저장·업로드·서버 검증·응답 검증·탈취·회수에서 같은 범위를 사용한다. 소모에 따른 레벨 증가와 융합·환생에 따른 별 증가가 안전 범위를 벗어나면 상태와 재료를 전혀 변경하지 않는다. 고레벨 저장·재시작과 서버 왕복 결과를 검사한다.

동료 환생은 `level >= 10`일 때 Lv1·별+1로 바뀌고 현재 힘 공식을 유지한다. 기본 힘 `P = max(1, floor(baseHp(bossIndex) / 20)) * level * 2 ** stars`를 공유 함수의 bigint 연산으로 계산한다. 같은 동료의 환생 후 기본 힘은 환생 전 힘의 `2 / level`이다. 예를 들어 Lv10은 1/5, Lv20은 1/10이므로 강화로 단정하지 않는다.

환생 버튼을 누르면 대상의 이름·레벨·별, 전후 기본 힘, Lv1·별+1 결과와 `환생 확인`/`취소`를 보여준다. 두 번째 확인이 있어야 실행한다. 확인 중 대상 ID·레벨·별이 바뀌거나 대상이 사라지면 기존 확인을 무효화한다. 힘을 결정하는 종·보스 깊이가 바뀌어도 기존 표시를 승인으로 재사용하지 않는다. 실행 직전에 같은 대상을 다시 검증하고 바뀐 대상에는 새 전후 표시와 확인을 요구한다. 사용자가 취소하면 상태가 바뀌지 않는다. 힘 표시는 현재 계산 결과를 사용하며 bigint를 부정확한 number로 변환하지 않는다.

메뉴의 확인 요청은 `{ type: 'reincarnate', id, expected: { speciesId, bossIndex, level, stars } }`로 표시 당시 대상 스냅샷을 반드시 보낸다. 동료 목록 갱신에서 대상이 변경·삭제되면 확인을 무효화하고, 무관한 저장 갱신에는 확인을 유지한다. 새 메뉴 IPC는 `expected`를 필수로 요구하고 누락 또는 필드 형식 오류를 거부한다. 실제 동료 상태를 소유한 core는 형식을 다시 검증하고 현재 대상의 같은 값과 일치하는지 확인한 뒤에만 상태를 변경한다. 불일치는 거부하여 마지막 UI 갱신 이후의 상태 변경도 보호한다. 내부 core 직접 호출만 `expected?: { speciesId, bossIndex, level, stars }`를 유지하여 기존 내부 호출과 측정기의 생략을 허용한다. 이 내부 호환은 새 메뉴/IPC의 필수 확인을 우회하는 경로로 쓰지 않는다.

### 도감과 레거시

영웅 공개는 실제 선택 이력 또는 영구 컬렉션, 몬스터 공개는 `speciesKills[id] > 0`으로 판단한다. 환생 후보 제시·필드 등장·PvP 획득만으로 공개하지 않는다. `seenHeroes`와 `seenMonsters`는 기존 추첨·해금 의미를 유지한다.

같은 공유 판정을 공개 수, 실루엣, 이름, 설명, 능력치, 접근성 라벨, 알림 미리보기, 미확인 수, ACK 허용 목록, 목표 완료에 적용한다. 도감 안내는 영웅을 실제로 선택하거나 몬스터를 처음 처치하면 공개된다고 설명한다. 자격을 만족해도 획득/처치 전의 도감 목표는 완료로 표시하지 않는다. 필드·환생 후보·PvP 파티 원화에는 이 실루엣 정책을 적용하지 않는다.

레거시에서 새 기준을 충족하지 못하는 공개 카드는 실루엣으로 돌리고 해당 ACK를 제거한다. 나중의 첫 선택·처치는 새로운 알림이 된다. 기록 없는 과거 처치를 보유 동료·누적 처치 수로 추정하지 않는다. codex 없는 구형 저장의 초기 ACK도 실제 증거가 있는 항목만 처리하며 엔진 부팅 경로에서 열린 후보를 다시 ACK하지 않는다. 실제 보유 영웅의 공개는 유지한다.

### PvP 디렉터리

기존 최대 50명 API와 지정 상대 선택을 사용한다. 각 행에 순위·영웅 원화·이름·승패·동료 파티 원화와 정보·선택 버튼을 표시한다. 목록에 이미 있는 파티 표시를 보존하고 선택한 상대의 ID·행 강조·미리보기·실제 매치 요청을 일치시킨다.

`PvpOpponent.playerId?: string`를 shared/server/net 인터페이스에 추가한다. 새 서버는 실제 상대의 미리보기와 전투 결과에 상대 ID를 반환하고 봇에는 ID를 붙이지 않는다. 기존 random·레거시·봇 응답은 optional 호환을 유지한다. 지정 상대 선택에서는 응답 ID가 요청 ID와 정확히 일치해야 성공으로 처리하며 이름으로 대신 확인하지 않는다. ID 누락·불일치 응답으로 미리보기나 전투를 진행하지 않는다.

주기 상태 업데이트에서 행과 버튼 DOM을 유지하여 키보드 포커스가 사라지지 않게 한다. Tab 이동과 Enter/Space 선택이 동작하고 선택 상태를 접근성 속성으로 전달한다. 이름을 포함한 선택 버튼 라벨로 같은 버튼을 구분한다. 목록 갱신으로 포커스 대상 행이 사라지면 새로고침 버튼으로 옮긴다. 상대 삭제·매치 만료·오프라인·빈 목록은 설명과 재시도 경로를 보이고 임의 상대와 자동 매치를 시작하지 않는다. 선택 요청 중 중복 선택을 막고 응답에서 실제 지정 상대가 맞는지 검증한다.

## 5. 비교·채택·검증 계약

탐색은 seed 10001–10020만 사용한다. 모든 대조와 후보를 120분 기준 정책에서 비교하고 첫 환생 성공 p50 45–60분 및 18/20의 90분 이내 성공을 모두 충족한 안을 같은 탐색 seed의 12시간 비교로 넘긴다. 12시간 비교에서는 최종 `h70` 자격 p50 8–12시간도 통과해야 한다.

두 목표를 통과한 대조·후보 사이에서 다음 순서로 채택한다.

1. 전체 표본의 `firstAccepted` p50이 52.5분에 가까운 안.
2. 같으면 최종 자격 p50이 10시간에 가까운 안.
3. 같으면 `firstAccepted` p90이 낮은 안.
4. 모두 같으면 프로토콜의 실험 ID 사전순.

어느 안도 통과하지 못하면 실패 원본을 보존하고 새 수치·가설·동결 시각으로 새 사전등록 라운드를 연다. 라운드당 성장 후보는 최대 3개다. 목표 범위나 분모를 바꾸어 통과시키지 않는다. 탐색에서 고른 안만 별도 검증 seed 1–100의 각 12시간에서 확인한다. 검증 seed로 튜닝하지 않으며 실패한 검증은 결과로 보존한다.

미도달은 `null`/미도달로 남기고 성공 표본만으로 전체 중앙값을 대체하지 않는다. 전체 표본 중앙값은 미도달을 모든 도달 시각 뒤에 놓아 계산하며, 90분 성공률의 분모는 항상 전체 20 또는 100이다. 마지막 named 자격의 전체 중앙값 역시 미도달을 포함한다. 최초 사건 p10/p50/p90, 준비→방문→성공 지연, 2시간에 남은 단계, 이후 새 해금/처치/선택, 발견 공백과 최악 정체를 보고한다.

검증 기준 정책을 유지하고 release에서는 설정의 9개 정책을 모두 측정한다. 같은 총입력의 균등/집중 입력, 즉시/2분/10분 메뉴 방문, 무료/훈련/미끼/재굴림, 무관리/소모/융합/동료 환생, active/intermittent/초기 활동 후 방치/순수 방치를 구분한다. 정책별 결과를 섞어 기준 정책의 성공으로 보고하지 않는다.

소스·컴파일 결과·프로토콜·평가 도구·초기 상태·행동 정책의 지문을 원본 측정에 묶는다. 변경 후 이전 실행 파일에 이어 쓰거나 원본 실패를 덮어쓰지 않는다. 영향받은 작업과 의존 작업을 다시 검증하며 작업의 등록 AC와 `npm test && npm run lint && npm run typecheck`가 같은 대상 소스에서 성공한 뒤에만 Host가 `verified`로 기록한다. 기존 테스트를 삭제·skip·약화하지 않는다.

V07-02의 UI 소유권은 `src/menu/view.ts`, `src/menu/index.ts`, `tests/menu.test.ts`다. 기존 메뉴 테스트의 한 번 클릭 환생 계약을 첫 클릭 시 미전송·전후 표시·확인 후 전송 계약으로 갱신한다. Host는 신규 `tests/companionLevelsV7.test.ts`와 core/save/IPC 및 해당 테스트, Balance는 shared/server/net 및 해당 테스트를 맡는다. 등록 `levels` AC는 `npx vitest run tests/companionLevelsV7.test.ts tests/menu.test.ts tests/ipc.test.ts`로 실행하여 고레벨·overflow와 실제 메뉴 확인 및 IPC 입력 계약을 함께 검증한다. 설정·저널과 AC 원본 보존은 Host가 관리한다.

## 6. 상태와 출시 증거

현재 round04는 사전등록·문서 갱신 상태이며 정식 검토는 대기 중이다. V07-01은 이전 검증 이력을 보존하고 새 검토를 위해 `running`으로 돌아갔으며 영향받은 후속 작업도 재검증 전 `pending`이다. 정식 설계 검토는 새 `reviews/design-round04`에서 `fun.mjs init/next`가 발급하는 전체 prompt/template으로 진행한다. 이 문서를 동결한 뒤 새 네 역할 검토와 등록 AC·게이트를 수행해야 하며, 과거 설계 검토·Native 진단·단위 테스트 통과를 새 round의 verified로 옮기지 않는다. 공통 tail 식은 이미 구현되었지만 새 후보 등록·설계 승인·수치 적용·새 측정·최종 출시는 각각 별도 상태다.

| 상태 | 뜻과 필요한 근거 |
| --- | --- |
| 하네스 준비 | H07-01 setup 근거. 현재 후보의 기능·재미·목표 통과를 뜻하지 않는다. |
| 설계 검토 완료 | 실제 별도 Designer→Critic→Balance→Playtester가 `fun.mjs next`의 전체 prompt/template에 응답하고 해당 입력 지문에서 verify 성공. 미래 측정 결과는 아직 미확인이다. |
| 분석 완료 | 실제 원본을 읽은 네 역할의 `audit.mjs` 결과. 미달·미확인과 출시 AC 상태를 그대로 남긴다. |
| 제품 출시 검증 | 최종 v0.7.0 소스의 작업 AC·게이트·측정·Native·독립 감사·smoke·실제 패키지·고레벨 서버 호환 증거가 모두 충족된 상태. |

Host가 Playtester와 저널·통합을 맡고 Designer/Critic/Balance는 서로 다른 실제 agent ID와 기본 모델로 실행한다. 동시 실행은 Host 포함 4슬롯이다. 독립 조사와 충돌 없는 파일 구현은 병렬로 하되 판단 순서는 Designer→Critic→Balance→Playtester다. Critic은 구현하지 않는다. 정식 설계 검토가 반려되면 사유·수정을 보존하고 갱신된 입력으로 새 round를 시작한다.

기능 구현 뒤 package/lock 버전을 먼저 0.7.0으로 고정하고 최종 근거를 만든다. release Native는 독립 5/15/30분 × active/idle/intermittent 9개와 별도 연속 180분 active 1개다. 긴 여정은 10분마다 실제 메뉴로 준비된 환생을 선택한다. 자연 관측에 fixture나 시간 가속을 쓰지 않고 격리 저장·합성 입력·모의 네트워크를 사용한다. 사용자 저장·전역 입력 훅·운영 PvP를 사용하지 않는다. 실행 중 측정/Native 프로세스를 확인해 중복 시작하지 않는다.

새 클라이언트 출시 전 고레벨 서버 호환을 확인한다. 로컬 서버 테스트와 운영 서버 호환 근거를 구분한다. 운영 배포·커밋·푸시는 자동 수행하지 않는다. 실행 범위, 실패, 미확인, 다음 행동은 Host가 ACCEPTANCE.md와 HANDOFF.md에 기록한다. 사람 관찰이 없으면 모든 자동 검증이 끝나도 `humanChecks=PENDING`을 유지한다.
