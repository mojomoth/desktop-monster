## 1. 목표와 첫 여정

기준 정책은 신규 저장,100ms tick, 균등2입력/초, 골드 미사용, 동료 무관리, 준비 즉시 첫 환생 후보 선택이다. 첫 영웅 환생의 성공 p50은45–60분, 전체 검증100개 중 최소90개는90분 안에 성공해야 한다. 마지막 named 콘텐츠의 자격 충족 p50은8–12시간이다. 사람의 재미·업무 방해·외형 선호는 별도 관찰 전까지 `humanChecks=PENDING`이다.

첫 환생 전에도 첫 처치·보상·레벨·포획과 다음 환생 레벨을 확인할 수 있어야 한다. 종별 처치 목표, 동료 확보, 원소와 영웅 선택이 다음 목표로 이어지게 한다. 숫자 증가나 반복 스택은 새 콘텐츠 해금으로 세지 않는다. 새 강제 시간 제한을 추가하지 않으며 기존 환생 휴식120초와 무료 보류30초는 유지한다. 준비·후보 제시·선택 성공은 각각 기록한다.

표의 최소 레벨은 `heroMinLevel`,보장 시작은 `firstCaptureBossIndex`,상한은 `earlyCaptureCount`다. 나머지는 모든 실험에서 `xpBase=20`, `companionHpNumerator=115`, `companionHpDenominator=100`, `captureChance=0.35`, `heroLevelStepEvery=2`, `heroLevelStepCap=6`, `heroRestMs=120000`, `heroDeferMs=30000`, `xpRewardBase=5`, `xpRewardPerIndex=3`, `bossXpMultiplier=5`, `bossHpMultiplier=5`다. 대조와 후보는 XP/보장도 다르므로 대조 차이를 HP만의 효과로 해석하지 않는다.

공통 식에서 `L`은 최소 영웅 환생 레벨, `r`은 누적 영웅 환생 횟수, `i`는0부터 시작하는 몬스터 깊이다.

- 요구 레벨은 `L + min(6, floor((r + 1) / 2))`,다음 레벨 XP는 `floor(20 * xpGrowth ** (level - 1))`다.

### 한도·정원·RNG·저장 계약

`earlyCaptureCount`는 기본1이며1–30의 양의 안전 정수다. 기존의 영구 할당 카운터 `nextCompanionId`가 이 상한 이하인 초기 구간에만 보장을 적용한다. 일반 저장에서 이 값은 정확한 자연 포획 횟수가 아니다. 성공한 PvP 전송도 카운터를 사용하고, 저장의 ID 충돌 보정은 명단의 ID 숫자를 따라 값을 더 높일 수 있다. 그 결과 보장 구간이 일찍 소진되거나 건너뛰어지는 기존 의미를 유지한다. 과거 획득 수를 역산하거나 카운터를 낮추고 초기화하지 않으며 새 저장 필드는 없다. 신규 저장·PvP 없는 기준 측정에서만 `nextCompanionId - 1`이 자연 포획 횟수와 같다.

보스에서 기존 포획 난수를 정확히 한 번 소비한 뒤 정상35% 추첨과 다음 보장을 OR한다. 비보스에서는 포획 난수를 소비하거나 보장하지 않는다.

```text
boss
&& firstCaptureBossIndex !== null
&& index >= firstCaptureBossIndex
&& nextCompanionId <= earlyCaptureCount
&& companions.length < 30
```

count1은 빈 정원이 있는 경우 기존 최초 포획 보장과 같은 카운터 조건이다. count5는 `nextCompanionId <= 5`인 동안 깊은 보스에서 보장한다. 신규 저장·PvP 없는 측정의0명 상태라면 조건을 충족하는 index63/71/79… 보스에서5번째 자연 포획 보관까지 보장하며, 이미4명을 자연 포획했다면 다음 적격 보스에서5번째만 보장한다. 이 예시는 일반 레거시/PvP 저장의 자연 포획 수를 추론하는 규칙이 아니다. 포획은 보스 처치 후에 발생하므로 해당 보스 처치 자체를 돕지 않는다. 첫5명 모두를 index63에서 즉시 주는 방식도 아니다.

정원30이면 보장은 꺼지고 기존35%에 따른 방출·영혼과 같은 RNG 소비만 유지한다. 낮은 할당 카운터와 가득 찬 명단이 함께 있는 경계 상태에서도 매 보스 강제 방출·영혼 보상이 반복되지 않게 한다. 이 정원 경계 보완은 count1 설정에도 적용하며 과거 full-roster 보장 동작과 완전히 같다고 주장하지 않는다. 자연 포획에서 보관하지 못한 동료는 카운터를 증가시키지 않는다. 외부 전송의 기존 할당 처리와 저장 ID 보정은 그대로 유지한다.

소비·희생·동료/영웅 환생·재시작으로 이미 소진한 보장 구간을 다시 켜지 않는다. 현재 명단이 줄었다고 카운터를 낮추지 않는다. 레거시 ID 보정이나 외부 전송으로 카운터가 이미 상한을 넘은 저장에는 과거 자연 포획이 적었을 가능성만으로 보장을 복구하지 않는다. 기존 포획의 종·깊이·Lv1·별0,30명 정원과 방출·영혼 동작을 유지한다. 새 시계·강제 대기·동료 레벨 상한·유료 조건을 추가하지 않는다.

영구 할당 안전과 count 보장은 Round06에서 구현했다. 저장의 모든 ID 숫자 보정은 유지하되 `Number.MAX_SAFE_INTEGER`를 상한/소진 표지로 쓰고,로컬 발급의 unsafe 증가와 중복 ID를 상태·재료 변경 전에 거부한다. 외부 s/r ID는 보존하고 카운터 증가는 안전 상한에서 포화시킨다. 과거 자연 포획 수를 역산하거나 기존 동료를 버려 보정을 맞추지 않는다.

당시 Host의955개 테스트·lint·typecheck와 독립 Critic 검토 성공,후보별 실제 엔진 검증은 **이전 소스의 구현 근거**다. 현재 새 HP 후보의 성능이나 같은 소스 AC/게이트 성공을 뜻하지 않는다. 구현을 다시 만들지 않고 새 프로토콜/소스에서 필요한 등록 검증을 다시 수행한다.

새 등록 검증에서도 count1의 비정원 기존 의미, index62/63/71 경계, 보장 직전/직후의 카운터1/4/5/6, count 범위1–30 및 잘못된 형식, 정상 추첨과 보장 각각의1draw, null/비보스 비활성, 낮은 카운터+정원30의 무보장과 정상 방출, 소비/희생/재시작 후 재무장 없음, 기존 PvP 할당·저장 ID 보정이 구간을 일찍 소진/건너뛰어도 역산·재무장하지 않는 경계, 실제 저장·엔진·worker·보고서의 매개변수 일치를 포함한다. 기존 테스트와 실패 근거를 삭제·약화·새 의미로 재인증하지 않는다.

## 4. 획득·동료 관리·PvP UI 계약

### 동료 레벨과 환생

동료 레벨은 양의 안전 정수 `number`로 유지하고 게임상 Lv10 상한을 제거한다. 저장·업로드·서버 검증·응답 검증·탈취·회수에서 같은 범위를 사용한다. 소모에 따른 레벨 증가와 융합·환생에 따른 별 증가가 안전 범위를 벗어나면 상태와 재료를 전혀 변경하지 않는다. 고레벨 저장·재시작과 서버 왕복 결과를 검사한다.

동료 환생은 `level >= 10`일 때 Lv1·별+1로 바뀌고 현재 힘 공식을 유지한다. 기본 힘 `P = max(1, floor(baseHp(bossIndex) / 20)) * level * 2 ** stars`를 공유 함수의 bigint 연산으로 계산한다. 같은 동료의 환생 후 기본 힘은 환생 전 힘의 `2 / level`이다. 예를 들어 Lv10은 1/5, Lv20은 1/10이므로 강화로 단정하지 않는다.

환생 버튼을 누르면 대상의 이름·레벨·별, 전후 기본 힘, Lv1·별+1 결과와 `환생 확인`/`취소`를 보여준다. 두 번째 확인이 있어야 실행한다. 확인 중 대상 ID·레벨·별이 바뀌거나 대상이 사라지면 기존 확인을 무효화한다. 힘을 결정하는 종·보스 깊이가 바뀌어도 기존 표시를 승인으로 재사용하지 않는다. 실행 직전에 같은 대상을 다시 검증하고 바뀐 대상에는 새 전후 표시와 확인을 요구한다. 사용자가 취소하면 상태가 바뀌지 않는다. 힘 표시는 현재 계산 결과를 사용하며 bigint를 부정확한 number로 변환하지 않는다.

메뉴의 확인 요청은 `{ type: 'reincarnate', id, expected: { speciesId, bossIndex, level, stars } }`로 표시 당시 대상 스냅샷을 반드시 보낸다. 동료 목록 갱신에서 대상이 변경·삭제되면 확인을 무효화하고, 무관한 저장 갱신에는 확인을 유지한다. 새 메뉴 IPC는 `expected`를 필수로 요구하고 누락 또는 필드 형식 오류를 거부한다. 실제 동료 상태를 소유한 core는 형식을 다시 검증하고 현재 대상의 같은 값과 일치하는지 확인한 뒤에만 상태를 변경한다. 불일치는 거부하여 마지막 UI 갱신 이후의 상태 변경도 보호한다. 내부 core 직접 호출만 `expected?: { speciesId, bossIndex, level, stars }`를 유지하여 기존 내부 호출과 측정기의 생략을 허용한다. 이 내부 호환은 새 메뉴/IPC의 필수 확인을 우회하는 경로로 쓰지 않는다.

### 도감과 레거시

영웅 공개는 실제 선택 이력 또는 영구 컬렉션, 몬스터 공개는 `speciesKills[id] > 0`으로 판단한다. 환생 후보 제시·필드 등장·PvP 획득만으로 공개하지 않는다. `seenHeroes`와 `seenMonsters`는 기존 추첨·해금 의미를 유지한다.

같은 공유 판정을 공개 수, 실루엣, 이름, 설명, 능력치, 접근성 라벨, 알림 미리보기, 미확인 수, ACK 허용 목록, 목표 완료에 적용한다. 도감 안내는 영웅을 실제로 선택하거나 몬스터를 처음 처치하면 공개된다고 설명한다. 자격을 만족해도 획득/처치 전의 도감 목표는 완료로 표시하지 않는다. 필드·환생 후보·PvP 파티 원화에는 이 실루엣 정책을 적용하지 않는다.

레거시에서 새 기준을 충족하지 못하는 공개 카드는 실루엣으로 돌리고 해당 ACK를 제거한다. 나중의 첫 선택·처치는 새로운 알림이 된다. 기록 없는 과거 처치를 보유 동료·누적 처치 수로 추정하지 않는다. codex 없는 구형 저장의 초기 ACK도 실제 증거가 있는 항목만 처리하며 엔진 부팅 경로에서 열린 후보를 다시 ACK하지 않는다. 실제 보유 영웅의 공개는 유지한다.

### PvP 디렉터리

기존 최대 50명 API와 지정 상대 선택을 사용한다. 각 행에 순위·영웅 원화·이름·승패·동료 파티 원화와 정보·선택 버튼을 표시한다. 목록에 이미 있는 파티 표시를 보존하고 선택한 상대의 ID·행 강조·미리보기·실제 매치 요청을 일치시킨다.

`PvpOpponent.playerId?: string`를 shared/server/net 인터페이스에 추가한다. 새 서버는 실제 상대의 미리보기와 전투 결과에 상대 ID를 반환하고 봇에는 ID를 붙이지 않는다. 기존 random·레거시·봇 응답은 optional 호환을 유지한다. 지정 상대 선택에서는 응답 ID가 요청 ID와 정확히 일치해야 성공으로 처리하며 이름으로 대신 확인하지 않는다. ID 누락·불일치 응답으로 미리보기나 전투를 진행하지 않는다.

주기 상태 업데이트에서 행과 버튼 DOM을 유지하여 키보드 포커스가 사라지지 않게 한다. Tab 이동과 Enter/Space 선택이 동작하고 선택 상태를 접근성 속성으로 전달한다. 이름을 포함한 선택 버튼 라벨로 같은 버튼을 구분한다. 목록 갱신으로 포커스 대상 행이 사라지면 새로고침 버튼으로 옮긴다. 상대 삭제·매치 만료·오프라인·빈 목록은 설명과 재시도 경로를 보이고 임의 상대와 자동 매치를 시작하지 않는다. 선택 요청 중 중복 선택을 막고 응답에서 실제 지정 상대가 맞는지 검증한다.

## 5. 비교·채택·검증 계약

탐색은 seed 10001–10020만 사용한다. 모든 대조와 후보를 120분 기준 정책에서 비교하고 첫 환생 성공 p50 45–60분 및 18/20의 90분 이내 성공을 모두 충족한 안을 같은 탐색 seed의 12시간 비교로 넘긴다. 12시간 비교에서는 최종 `h70` 자격 p50 8–12시간도 통과해야 한다.

두 목표를 통과한 대조·후보 사이에서 다음 순서로 채택한다.

1. 전체 표본의 `firstAccepted` p50이 52.5분에 가까운 안.
2. 같으면 최종 자격 p50이 10시간에 가까운 안.
3. 같으면 `firstAccepted` p90이 낮은 안.
4. 모두 같으면 프로토콜의 실험 ID 사전순.

어느 안도 통과하지 못하면 실패 원본을 보존하고 새 수치·가설·동결 시각으로 새 사전등록 라운드를 연다. 라운드당 성장 후보는 최대 3개다. 목표 범위나 분모를 바꾸어 통과시키지 않는다. 탐색에서 고른 안만 별도 검증 seed 1–100의 각 12시간에서 확인한다. 검증 seed로 튜닝하지 않으며 실패한 검증은 결과로 보존한다.

미도달은 `null`/미도달로 남기고 성공 표본만으로 전체 중앙값을 대체하지 않는다. 전체 표본 중앙값은 미도달을 모든 도달 시각 뒤에 놓아 계산하며, 90분 성공률의 분모는 항상 전체 20 또는 100이다. 마지막 named 자격의 전체 중앙값 역시 미도달을 포함한다. 최초 사건 p10/p50/p90, 준비→방문→성공 지연, 2시간에 남은 단계, 이후 새 해금/처치/선택, 발견 공백과 최악 정체를 보고한다.

검증 기준 정책을 유지하고 release에서는 설정의 9개 정책을 모두 측정한다. 같은 총입력의 균등/집중 입력, 즉시/2분/10분 메뉴 방문, 무료/훈련/미끼/재굴림, 무관리/소모/융합/동료 환생, active/intermittent/초기 활동 후 방치/순수 방치를 구분한다. 정책별 결과를 섞어 기준 정책의 성공으로 보고하지 않는다.

소스·컴파일 결과·프로토콜·평가 도구·초기 상태·행동 정책의 지문을 원본 측정에 묶는다. 변경 후 이전 실행 파일에 이어 쓰거나 원본 실패를 덮어쓰지 않는다. 영향받은 작업과 의존 작업을 다시 검증하며 작업의 등록 AC와 `npm test && npm run lint && npm run typecheck`가 같은 대상 소스에서 성공한 뒤에만 Host가 `verified`로 기록한다. 기존 테스트를 삭제·skip·약화하지 않는다.

V07-02의 UI 소유권은 `src/menu/view.ts`, `src/menu/index.ts`, `tests/menu.test.ts`다. 기존 메뉴 테스트의 한 번 클릭 환생 계약을 첫 클릭 시 미전송·전후 표시·확인 후 전송 계약으로 갱신한다. Host는 신규 `tests/companionLevelsV7.test.ts`와 core/save/IPC 및 해당 테스트, Balance는 shared/server/net 및 해당 테스트를 맡는다. 등록 `levels` AC는 `npx vitest run tests/companionLevelsV7.test.ts tests/menu.test.ts tests/ipc.test.ts`로 실행하여 고레벨·overflow와 실제 메뉴 확인 및 IPC 입력 계약을 함께 검증한다. 설정·저널과 AC 원본 보존은 Host가 관리한다.

## 6. 상태와 출시 증거

현재 round08은 사전등록·문서 갱신 상태이며 정식 검토는 대기 중이다. V07-01은 이전 검증 이력을 보존하고 새 검토를 위해 `running`으로 돌아갔고, 영향받은 후속 작업은 같은 입력에서 새 검증 전까지 현재 `verified`로 다루지 않는다. 정식 설계 검토는 새 `reviews/design-round08`에서 `fun.mjs init/next`가 발급하는 전체 prompt/template으로 진행한다. 이 문서를 동결한 뒤 실제 Designer→Critic→Balance→Host Playtester와 등록 AC·게이트를 수행한다. 과거 역할 검토·Native 진단·단위 테스트를 현재 round의 성공으로 옮기지 않는다. 공통 tail/할당 안전/초기 보장은 이미 구현했지만,새 HP 등록의 역할 검토·같은 소스 AC/게이트·후보 측정·결과 감사·최종 출시는 각각 별도 상태다.

| 상태 | 뜻과 필요한 근거 |
| --- | --- |
| 하네스 준비 | H07-01 setup 근거. 현재 후보의 기능·재미·목표 통과를 뜻하지 않는다. |
| 설계 검토 완료 | 실제 별도 Designer→Critic→Balance→Playtester가 `fun.mjs next`의 전체 prompt/template에 응답하고 해당 입력 지문에서 verify 성공. 미래 측정 결과는 아직 미확인이다. |
| 분석 완료 | 실제 원본을 읽은 네 역할의 `audit.mjs` 결과. 미달·미확인과 출시 AC 상태를 그대로 남긴다. |
| 제품 출시 검증 | 최종 v0.7.0 소스의 작업 AC·게이트·측정·Native·독립 감사·smoke·실제 패키지·고레벨 서버 호환 증거가 모두 충족된 상태. |

Host가 Playtester와 저널·통합을 맡고 Designer/Critic/Balance는 서로 다른 실제 agent ID와 기본 모델로 실행한다. 동시 실행은 Host 포함 4슬롯이다. 독립 조사와 충돌 없는 파일 구현은 병렬로 하되 판단 순서는 Designer→Critic→Balance→Playtester다. Critic은 구현하지 않는다. 정식 설계 검토가 반려되면 사유·수정을 보존하고 갱신된 입력으로 새 round를 시작한다.

기능 구현 뒤 package/lock 버전을 먼저 0.7.0으로 고정하고 최종 근거를 만든다. release Native는 독립 5/15/30분 × active/idle/intermittent 9개와 별도 연속 180분 active 1개다. 긴 여정은 10분마다 실제 메뉴로 준비된 환생을 선택한다. 자연 관측에 fixture나 시간 가속을 쓰지 않고 격리 저장·합성 입력·모의 네트워크를 사용한다. 사용자 저장·전역 입력 훅·운영 PvP를 사용하지 않는다. 실행 중 측정/Native 프로세스를 확인해 중복 시작하지 않는다.

새 클라이언트 출시 전 고레벨 서버 호환을 확인한다. 로컬 서버 테스트와 운영 서버 호환 근거를 구분한다. 운영 배포·커밋·푸시는 자동 수행하지 않는다. 실행 범위, 실패, 미확인, 다음 행동은 Host가 ACCEPTANCE.md와 HANDOFF.md에 기록한다. 사람 관찰이 없으면 모든 자동 검증이 끝나도 `humanChecks=PENDING`을 유지한다.
