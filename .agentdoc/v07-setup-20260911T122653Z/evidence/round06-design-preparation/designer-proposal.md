# Round06 탐색 사전등록 전 Designer 제안

작성: 실제 agent `/root/designer`. **미등록·미측정 제안**이다. 아래 숫자는 Host의 독립 검토를 위한 후보이며, 정식 fun 검토·목표 통과·채택 판단이 아니다.

읽은 범위는 `src/core/{progression,formulas,engine,hero}.ts`, 탐색 `round-01`, `round-02`, `round-05`와 각각의 `round01/02/05-analysis`뿐이다. `candidate.json`, `validation-*`, 최신 HANDOFF/ACCEPTANCE는 읽지 않았다. 검증의 수치·개별 seed를 제안에 사용하지 않았다. 새 실행·측정·빌드·테스트·원본 수정 없이 이 문서만 작성했다.

후기의 운과 첫 환생 순위도 구분해야 한다. Round05 tail10475의10006은 첫 성공1840.5초였지만2시간에30명·힘136221이고,8시간1901처치→12시간2505처치로4시간604처치만 늘었다.10018은 첫 성공이5453.5초로 늦었지만8시간58440처치→12시간99837처치였다. 전체 파티는 자동 교체되지 않으며, 정원이 찬 뒤 포획은 해제와 영혼으로 처리된다(`engine.ts:255–265`). 이 제안의 초기 포획 보장은 후기30칸의 성능 분산을 없애지 않는다.

근거는 각 실험의 `screening.json.runs/*/<seed>.json`, Round05 해당 후보의 `full-12h.json.runs/*/<seed>.json`, 세 분석 폴더의 `README.md`/`final-analysis.json`이다. 원본에는 전체 포획 난수·모든 포획 깊이의 연속 trace가 없으므로, 포획이 지연에 기여한 비율이나 모든 RNG 분기를 복원했다고 주장하지 않는다.

## 승인될 경우의 최소 생산 구현 계약

1. `ProgressionParameters`에 숫자 `earlyCaptureCount` 하나만 추가한다. 기본1은 명단 여유가 있을 때 기존 first-capture 의미와 같다. 아래 정원30 예외는 A에도 적용할 공통 보완이며, 기존 full-roster 보장 동작과까지 완전히 같다고 주장하지 않는다. 이번 후보 값은1 또는5이며 양의 안전 정수로 검증한다. depth는 기존 `firstCaptureBossIndex`를 재사용하고 null이면 보장하지 않는다. A와 모든 기존 대조는 새 스키마에서 count1로 명시한다.
2. 보스당 기존 RNG를 정확히 한 번 소비한 뒤, 보장 조건만 `firstCaptureBossIndex !== null && state.nextCompanionId <= earlyCaptureCount && killed.index >= firstCaptureBossIndex && state.companions.length < ROSTER_CAP`로 확장한다. 일반 `captureRoll < 0.35`와 OR하며 정상 포획을 대체하지 않는다. 비보스는 보장하지 않는다. 정원30일 때는 새 보장을 적용하지 않고 기존35% 추첨에 따른 해제·영혼만 유지한다. 보관에 성공해야 카운터가 증가하므로, 외부 전송 등으로 낮은 카운터와 가득 찬 명단이 함께 존재해도 매 보스 강제 해제·영혼 보상이 반복돼서는 안 된다. 새 시계·대기·레벨 제한·선택 정책을 추가하지 않는다.
3. 기존 단조 증가 `nextCompanionId`를 사용하고 새 저장 필드는 만들지 않는다. 새 게임은1에서 시작하고 저장 재개 시 그대로 읽는다(`engine.ts:93–128`). count5에서는0명 획득 상태의 index63/71/79… 보스가 조건을 충족할 때 최대5번째 영구 획득까지 보장하며, 이미4명을 획득했다면 다음 적격 보스에서5번째만 보장한다.6이 되면 꺼진다. 이 카운터는 PvP 등 외부 획득 총량을 새로 추론하는 용도로 사용하지 않는다. 영웅 환생의 Lv1 복귀는 동료/카운터를 지우지 않는다(`hero.ts:297–319`). 소비·희생으로 명단을 줄이거나 재시작해도 소진한 한도가 다시 켜져서는 안 된다. 보관 실패/정원 해제는 한도를 소모하지 않지만, 가득 찬 명단에는 보장 자체가 적용되지 않는다.
4. 현재 저장·동료 레벨·서버 피해·소유권 계약은 유지한다. 포획 대상/종/레벨1/별0, 정원30의 해제·영혼 동작도 유지한다. `monsterMaxHp`의 동료115/100과 BigInt 단일 나눗셈을 변경하지 않는다.
5. 공식 등록을 할 때 매개변수 버전을 새21키 계약으로 올리고, 기존17/20키 원본 읽기와 검증은 그 버전대로 보존한다. 실제 생산 export·컴파일 worker·보고서·프로토콜의21키 전부를 일치시켜야 한다. CLI ID만으로 새 조건을 대체해서는 안 된다. 이것은 구현 요청의 제안이며 현재 스키마가 바뀌었다는 뜻이 아니다.

필요한 새 검증은 count1의 기존 동작 일치, index62/63/71 경계, 카운터1/4/5/6과 보장 직전/직후 한도 경계, 정상 추첨 성공과 보장 성공 각각의 정확한1회 RNG 소비, 비보스 제외, null 비활성, 소비/희생/재시작/영웅 환생 이후 비재활성, 낮은 카운터+정원30에서 무보장 및 기존35% 해제·영혼 동작, 실제 엔진→worker→보고서 binding이다. 기존 first-capture tests와 과거 원본을 삭제하거나 새 의미로 재인증하지 않는다. 현재 읽기 범위 밖 저장/컬렉션 경계는 구현 담당자가 실제 코드와 등록 AC로 확인해야 한다.

## 판정과 남는 불확실성

- 먼저 새 등록·정식 Designer→Critic→Balance→Host Playtester 검토를 거친다. 탐색10001–10020의 같은20개로 각 후보와 Lv16–20 대조를 새로 실행한다.120분 선별은 성공 p50 2700–3600초와90분 이내18/20을 함께 요구하며, 전체 표본 분위수·성공자 조건부 분위수·미도달을 분리한다. 목표 중심3150초와 기존 tie-break를 유지한다.
- 선별 통과안만 같은 탐색 seed의12시간으로 진행하고, h70 자격 전체 p50 28800–43200초도 함께 통과해야 채택 후보가 된다. 같은 후보의 screening/full12h에 기록된 첫 경로는 새로 짝지어 검증한다. 과거 후보와 전체 prefix가 같다고 요구하거나 주장하지 않는다.
- 여섯 콘텐츠 조건은 그대로다: crownwyrm=dragon3, rootcolossus=환생3, h58=water100+reefknight2+총1500, h62=환생5+seenMonsters60+총6000, starvoid=환생10+총16000, h70=uniqueHeroes10+총30000. 희귀 영웅의 자격/제시/실제선택을 분리하며 무료 choices[0] 정책을 바꾸지 않는다.
- 5명 이후의 깊은 포획 운,30명 정원 이후 같은 파티의 지속, 과도한 후기 속도와 새로운 획득의 소진은 남는다.2/4/8/10/12시간 파티힘·획득수·정원 도달과 같은 seed의8→12시간 처치/환생/새 획득 공백을 함께 봐야 한다. 첫 목표를 통과했다고 이 위험이 해소됐다고 쓰지 않는다.
- 어느 후보도 두 목표를 통과하지 못하면 미채택으로 보존하고 새 사전등록을 한다. 검증 seed1–100로 숫자를 튜닝하거나 실패자를 분모에서 빼지 않는다. 설계 제안·구현 검증·탐색 분석·제품 출시 검증은 서로 다른 상태이며 사람 관찰은 `humanChecks=PENDING`이다.
